# 模型架构：多视角时序策略（v0.5）

> 目标：把 12 篇论文里被实测有效的机制，落到「单臂 + 动态传送带 + 水果分拣」这一具体任务上。
> 代码：`src/fruitsort/models/vision_policy.py` · 训练：`scripts/train_vision_policy.py`

## 1. 总体结构

```text
                 ┌── overhead RGB (T 帧) ──┐
                 │                         ├─ 共享 CNN（RGB + 帧差 4 通道）→ 128
                 ├── wrist RGB   (T 帧) ───┘
                 │
                 ├── 状态 49 维 (T 帧) ──── MLP → 128
                 │
                 └── 任务/类别 embedding → 128
                                │
                    + 视角类型编码 + 时间位置编码
                                │
                    Transformer ×4 层（因果掩码，8 头）
                                │
                             [CLS]
                          ┌─────┴─────┐
                动作分块头 K=8×4    未来预测头 H=4×24
                (目标位姿+夹爪)      (4 类水果 pos+vel)
```

## 2. 论文 → 模块映射

| 机制 | 来源论文 | 本项目的实现 |
| --- | --- | --- |
| 多视角输入（固定 + 腕部） | StreamPI / FASTER / TEMPO | overhead + `panda_wristcam` 手眼相机，共享 CNN |
| 帧差作为运动线索 | DynamicWAM / Reflex | 图像 4 通道：RGB + \|I_t − I_{t−1}\| |
| 历史 T 帧 + 因果注意力 | StreamPI 原子时间单元 | T=5，时间位置编码，token 级因果掩码 |
| 动作分块（chunk） | ACT / FASTER / DiscreteRTC | K=8，每步重规划取第 0 步 |
| 未来状态预测辅助任务 | AHEAD / DynamicWAM / TrajWAM | 辅助头预测未来 4 步 × 4 类的 pos/vel |
| 任务/语言条件 | NEO / VLA | 类别 embedding（预留文本编码器接口） |
| 预测与抓取解耦 | AHEAD / TrajWAM | 辅助头只做表征学习，抓取仍由动作头输出目标位姿 |
| 延迟感知执行 | LIBERO-Dynamic / FASTER | 训练时随机丢帧（待加），推理每步重规划 |

## 3. 模块细节

### 视觉编码器（共享）

```text
Conv(4→24, k5,s2) → BN → ReLU
Conv(24→48, k3,s2) → BN → ReLU
Conv(48→96, k3,s2) → BN → ReLU
Conv(96→96, k3,s2) → BN → ReLU
AdaptiveAvgPool → 96 维
```

- 输入 **96×96**（overhead 从 640×480 下采样，wrist 原生 128→96）
- 第 4 通道是相邻帧差，零成本运动特征

### 时序 Transformer

| 项 | 值 |
| --- | --- |
| d_model | 96 |
| 层数 / 头数 | **2 / 4** |
| FFN | 384 |
| 历史 | T = 4（20 Hz 下 0.2 s） |
| 序列长度 | 1 + T×(2 视角 + 1 状态) + 1 指令 = 14 |
| 掩码 | 因果；CLS 看全部 |

### 输出头

- **动作头**：`Linear(96 → 32)` → `(K=8, 4)`，目标 = 世界坐标 (x, y, z) + 夹爪
- **未来头**：`Linear(96 → 72)` → `(H=3, 4 类 × 6)`，预测未来 pos/vel（辅助损失权重 0.2）
- **指令**：类别 id ∈ {all, apple, strawberry, banana, pear} → embedding，加到 CLS

## 6.3 达成指标（v0.8）

**四类同场**基准（`scripts/benchmark_sorting.py`，四个水果同时在传送带上，带速 0.08 m/s）：

| 执行形态 | 成功率 | 单件节拍（均值 / P90） |
| --- | --- | --- |
| **模型选择 + 伺服**（teacher，20 episodes） | **19/20 = 95.0%**（CI 76.4–99.1） | **2.82 s / 3.02 s** |
| 模型选择 + 几何执行器（hybrid，40 episodes） | **39/40 = 97.5%**（CI 87.1–99.6） | 3.97 s / 4.21 s |

按类别（hybrid，各 10 次）：苹果 100%、草莓 100%、香蕉 90%、梨 100%。
按类别（teacher，各 5 次）：苹果 100%、草莓 100%、香蕉 80%、梨 100%。

- 节拍口径：水果进入抓取区 → 放置完成（不含传送带上的等待）
- 指令选择：**96/96 = 100%**（四类，`scripts/eval_selection.py`）
- 目标：成功率 ≥85%、单件 ≤7 s —— **两项均达标**

关键修复：
1. 梨改为更圆回转体（h70/r30），并降摩擦 0.8、提高角阻尼 3.0 —— 消除长距离侧滚（梨 4 类场景 40% → 100%）
2. 香蕉/梨放宽触底判定（0.045）—— 下探会顶到带面，不再卡在 DESCEND
3. 抓取后先 1.5 cm/步垂直抬 5 cm 再搬运 —— 避免甩飞

## 6.4 自蒸馏与延迟增强（v0.7）

- **自蒸馏**：用 5/5 的 teacher（模型+伺服）重新采集 24 条示教，访问分布正是纯模型需要的
- **延迟增强**：训练时以 0.2 概率把最后一帧替换为上一帧（模拟 1 帧推理/感知延迟）
- 结果：**纯模型闭环仍然 0/5**，模型+伺服保持 5/5
- 结论：分布漂移不是靠"补数据分布"就能解决，闭环纠偏层是结构性的

**预测驱动伺服的尝试**：把未来预测头接进伺服（AHEAD 思路），但未来头未学会——
预测 0.1 s 后的水果位置平均误差 **0.96 m**（退化为均值），因此不可用。
当前伺服用 `水果位置 + v·0.10`，苹果/草莓 5/5。

## 6.45 标签 bug 与纯策略突破（v0.11）

**根因**：`ScriptedSorter._action` 把 `last_target` 存成了"限速后的 6cm 目标"，
所有示教标签都变成 `目标 ≈ 当前 TCP`，模型因此学成悬停不动点。

修复后（标签 = FSM 真实目标）：

| 策略 | 0.08 m/s，苹果，5 episodes |
| --- | --- |
| 修复前（限速标签） | 0/5 |
| **修复后（raw 标签）** | **2/5 = 40%** |
| 修复后 + 学习式残差（+8cm 预算） | 1/5（噪声内，未改善） |

0.30 m/s 纯策略：0/4（示教只有 0.04–0.08 m/s，速度分布外）。

结论：悬停不动点确实是标签 bug，修复后纯策略能动了；但要到可用成功率还需要
更多示教（当前 33 条）与高速数据，以及残差的正确形态（TCP 相对增量 + 在环 DAgger）。

## 6.46 纯策略 + 吸盘（v0.12 进行中）

用吸盘控制器在 0.15/0.30 m/s 采 100 条成功示教，与 33 条 raw 标签示教混合训练
（`runs/vpolicy-mix`，val 0.10），再用 `eval_policy_suction.py` 评测：
策略输出接近/吸附触发/搬运/释放，吸盘只做附着物理。

| 训练数据 | val loss | 0.30 m/s 闭环 |
| --- | --- | --- |
| raw 33（0.08） | 0.45 | 2/5（苹果，40%） |
| raw + suction 100 | 0.10 | 苹果 2/5；四类 1/16 |
| + DAgger 24（157 条） | 0.33 | **0/16** |
| 仅 suction 100 | **0.064** | **0/16** |

结论：**拟合越好、闭环越差**——这是典型的闭环分布漂移。策略在 0.3 m/s 下无法稳定进入
「距水果 10 cm」的吸附窗口；手写吸盘控制器是 24/24。

尝试过的补救：动作块 open-loop 执行（0/4）、DAgger（更差）、delta 动作（0/5）、
学习残差 8 cm（1/5）。当前 0.41M MLP+2 层 Transformer + ~150 条示教不足以覆盖高速闭环。

## 6.47 相位门控对照（v1.0.1）

在纯策略上加几何相位门控（未抓住前强制接近、禁止切搬运）：

| 配置（0.08 m/s，苹果，5 episodes） | 成功率 |
| --- | --- |
| 纯策略（模型目标+模型夹爪） | 2/5 = 40% |
| 纯策略 + 相位门控 | **0/5** |

门控把模型输出完全覆盖成几何目标，等价于退化成脚本控制器（且没有搬运段逻辑），
因此更差。结论：在当前数据/架构下，纯策略与硬门控都不成立；
要么 500+ 示教 + ACT/DP，要么接受分层执行（模型选意图 + 伺服/执行器）。

## 6.48 大规模示教 + ACT（v1.1 实验）

- 用验收配置采 **367 条成功示教**（0.25 m/s / 30 Hz / 平行夹爪）
- ACT-lite 6.87M 训练 80 epochs：val 0.108，xyz 0.005
- 纯策略 0.25 m/s 苹果：**0/5**
- 轨迹诊断：**ACT 跟踪是好的**（t=30 时 TCP 与苹果重合），但闭爪相位错误
  （t=90 时水果已到 x=0.26，TCP 在 0.32 才闭爪），close_rate 0.53 但时机错
- ACT 运动 + 几何闭爪：**0/5**（目标悬停高度 0.57 vs 果心 0.48，闭爪窗口不满足）

结论：数据量从 33→367、模型 0.41M→6.87M 都没有改变闭环结果；
瓶颈是「接触时刻的相位/时序」，不是拟合或容量。要解决需要相位监督 +
大规模在环 DAgger（每次迭代重新采集数千条），超出单轮会话成本。

## 6.49 真正的失败机制：目标 z 的「分支被平均」（v1.2 诊断）

之前把闭环失败归因于「闭爪相位偏晚」，进一步追到根因：**目标 z 有三个分支被
单峰回归平均掉了**。示教标签（`scripted._action` 的真实目标）在同一状态下是：

| 段 | 目标 z | 触发条件 |
| --- | --- | --- |
| 接近（TRACK） | 果心 + 0.09 | 还没对齐 |
| 下探（DESCEND） | 果心（0.46–0.48） | 已对齐 + 在抓取区 |
| 搬运（CARRY） | 0.60 | 已抓起 |

模型看到的历史里不含「我在哪一段」，于是输出落在中间解（0.50–0.57），
永远不进入 `z <= grasp_z+0.015` 的闭爪窗口；等它闭爪时水果已经过去
（实测：苹果 x=0.26 时 TCP 才在 x=0.32 闭爪）。

相位标签可以从示教动作反推，且与专家闭爪率对齐（apple 搬运段 0.36 + 下探 0.36）：

```
d500-apple      接近 0.28  下探 0.36  搬运 0.36   （闭爪率 0.586）
d500-strawberry 接近 0.46  下探 0.24  搬运 0.30
d500-banana     接近 0.56  下探 0.19  搬运 0.25
d500-pear       接近 0.66  下探 0.22  搬运 0.12
```

对应改动（`--phase`）：
1. 状态追加 3 维 1-hot(接近/下探/搬运)，obs_dim 49→52
2. 新增相位辅助头（3 类 CE，每步监督），推理端用 k=0 的 argmax 作为**下一步输入**
   —— 相位由策略自己预测，不是脚本谓词
3. 进入/退出「搬运」只由真实夹持信号（`is_grasping`）决定，抓空 20 步自动回退，
   消除示教里不存在的「单向门」

## 6.50 DAgger 首轮的两条负结果（v1.2）

1. **只加 DAgger 数据不改善闭环**：`d500(367 条) + dagger-r1b(24 条)` 重训 ACT，
   val 从 0.108 恶化到 1.07，0.25 m/s 四类纯策略 **0/12**（每类 3 episodes）。
2. **DAgger 数据会污染相位头**：同一批数据加 `--phase`，验证集相位 CE 从 0.093
   涨到 1.31（只用 d500 时 4 epoch 就到 0.093）。

原因：r1b 的标签是「学生悬停状态下由几何规则打的标」。学生从未进入抓取窗口，
于是 99% 的帧被标成「接近」，其中 apple 的下探+搬运帧只有 1%。这等于教模型
「永远悬停」。DAgger 只有在学生已经会抓、只需要纠偏时才有增益；学生在抓取前
就停住时，几何重标注会退化成「悬停在远处」。

处置：相位策略只用 d500 的干净示教训练；DAgger 留到学生能进抓取窗口之后再开。

## 6.51 绝对目标位姿 = 轨迹回放（v1.2 trace 证据）

相位条件化训练收敛（val 0.117，相位 CE 0.0165 ≈ 离线 3 类几乎满分），但 0.25 m/s
四类闭环仍 **0/12**。差别在于：模型现在**会进入下探段**（apple 626/900 步），
但从不闭爪、从不进入搬运段。单局 trace：

```
t= 30 tcp=[-0.28 -0.01 0.56] apple=[-0.26 -0.04 0.48]  tgt=[-0.27 -0.01 0.57]  ← 重合
t= 50 tcp=[-0.22  0.01 0.54] apple=[-0.09 -0.04 0.48]  tgt=[-0.24  0.00 0.54]  ← 目标落后 15cm
t= 90 tcp=[-0.06 -0.01 0.48] apple=[ 0.25 -0.04 0.48]  tgt=[-0.04  0.00 0.47]  ← 落后 31cm，此处才闭爪
t=140 tcp=[ 0.13  0.13 0.56] apple=[ 0.45 -0.04 0.48]  tgt=[ 0.12  0.14 0.57]  ← tgt==tcp，机械臂冻结
```

**根因不是相位，也不是容量**：绝对目标位姿让 BC 退化成「按历史回放轨迹」。
示教标签来自一个**闭环伺服**（目标永远比当前 TCP 超前 ≤6cm），模型学到的映射是
「给定这段历史 → 轨迹上的这一点」，既不含也没有学到“误差→修正”。
一旦实际 TCP 落后于水果，模型输出的目标仍然停在与水果接触过的那个点，
误差没有负反馈通路，于是滞后单调增长，最后目标与当前位姿重合（`tgt==tcp`），
手臂彻底停住。

对应处置：改用 **TCP 相对增量**（`--delta-actions`，标签 = 专家目标 − 当前 TCP，
幅度中位数 15cm，执行端裁剪到 6cm 保留方向）。这样模型输出的是反馈量本身，
滞后在每一步被自动修正。

## 6.52 增量模式 + 安全界限：仍 0/12（v1.2 收口）

`--delta-actions --phase` 训练收敛（val 0.169，相位 CE 0.015），单局 trace 显示跟踪
滞后确实变短（`t=20` 时 TCP 已与苹果 xy 重合），但出现两种新失败：

1. **提前闭爪**：水果还在 16 cm 外就闭爪（相位头把「下探」判早了）。
2. **下探锁死**：相位停在「下探」，模型持续输出 6 cm/步的向下增量，压到带面后
   PD 饱和，手臂整体冻结（`dx` 恒定 −0.58，`tgt==tcp`）。

加了两条部署端安全界限后（目标 z 不低于果心 +5 mm；水果被越过 8 cm 时解除下探段）：

| 配置（0.25 m/s，苹果，3 episodes） | 结果 | 闭爪率 | 下探步数 |
| --- | --- | --- | --- |
| 绝对目标 + 相位 | 0/3 | 0.06 | 597–626（锁死） |
| 增量 + 相位（无界限） | 0/3 | 0.07 | 全程锁死 |
| 增量 + 相位 + 安全界限 | **0/3** | 0.12 | 21–39（能退出） |

安全界限把「锁死」变成了「能退出重试」，但抓取仍未发生：模型在水果进入抓取窗口
的那几帧没有闭爪。至此为止，本轮共 4 次训练 / 3 组闭环评测，纯策略在 0.25 m/s
四类合计 **0/21**（每类 3 episodes，另加多组苹果复测）。

**结论**：单峰回归 + 367 条示教无法覆盖「闭爪时刻」这个窄时间窗；数据里的
专家标签是**带历史的 FSM** 输出（同一状态在不同相位下有不同标签），
BC 学到的必然是轨迹回放而非反馈律。要跨过这一步需要状态反馈专家打标
（DAgger with a state-feedback teacher）或 10× 量级的、带恢复动作的示教。

## 6.53 增量标签修正后首次非零（v1.3）

把增量标签从「原始目标差」改成**实际执行位移**（每步裁剪到 ±6cm，chunk 内每步用各自的
TCP）后重训（`runs/act-phase-delta2`，val 0.145，相位 CE 0.0154）：

| 配置（0.25 m/s，苹果，3 episodes） | 结果 | 闭爪率 | 下探步数 | 搬运步数 |
| --- | --- | --- | --- | --- |
| 绝对目标 + 相位 | 0/3 | 0.06 | 597–626 | 0 |
| 增量（原始差） | 0/3 | 0.07 | 锁死 | 0 |
| **增量（执行位移）** | **1/3 = 33%** | 0.05–0.62 | 4–34 | 0 / 0 / 77 |

成功的那一局 `carry=77`：策略自己闭爪、抬起、搬过中点、到框上方、开爪落入——这是
**抓取与搬运第一次全部由策略输出**完成（无脚本执行器）。失败局的特征是几乎不进
「下探」段（descend 4–32 步），说明剩下的瓶颈是相位/闭爪时机的**触发率**，而不是
表达能力。

## 6.54 动作块与前馈超前（v1.3 收口，均无改善）

在 `runs/act-phase-delta2`（苹果 1/3）上试两种部署端改动：

| 配置（0.25 m/s，苹果，3 episodes） | 结果 | 现象 |
| --- | --- | --- |
| 每步重规划（s=1） | 1/3 | descend 4–34 步，迟疑 |

1. **同分布重采**：0.25 m/s 权重在 0.08 下闭爪率 0.00（0/5）——速度变了必须重采。

2. **增量动作标签 = 实际执行位移**（裁剪 ±6cm，chunk 内每步用各自 TCP）。

`--grip-ema 0.6`（夹爪 logit 平滑）、`--carry-latch`（搬运段连续 3 步预测开爪才松手）、

## 6.13 提高控制频率到 60 Hz（v1.10，负结果）

假设：0.20 m/s 的闭爪窗口只有 ±3 帧（30 Hz），把控制频率提到 60 Hz 应变成 ±6 帧。

**顺带修掉一个真 bug**：`ScriptedSorter` 的时间常量（`close_steps=12`、看门狗 500 步、
渐进闭爪 `counter/8`、搬运 90 步看护）是按 30 Hz 设计的；60 Hz 下同样的步数只有一半
真实时间，专家抓不住（草莓 0/50）。改成 `rate = control_freq/30` 后全部按比例缩放，
60 Hz 专家恢复（0.20 m/s 草莓 6/6）。同时 `record_demos/eval_act_pure` 的 `sim_freq`
映射修正为 20/30/60 → 100/120/240。

训出 `act-60hz-4c`（val 0.059）。评测（0.20 m/s，四类各 6 局）：

| 配置 | 苹果 | 草莓 | 香蕉 | 梨 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 30 Hz（`act-high-4c`，8 局/类） | 4/8 | 4/8 | 4/8 | 0/8 | 12/32 = 37.5% |

## 6.15 触觉传感：视觉+触觉联合（v1.12，负结果 + 可复用管线）

### 6.15.1 触觉信号（仿真真值，9 维）

`bc.build_tactile`：左右指净接触力 → 法向力 `Fn`、不平衡度 `Fasym=|fL_n−fR_n|/Fn`、
摩擦利用率 `rho=|F_t|/Fn`、夹爪开口 `w`、挤压比 `δ`、物体相对 TCP 速度 `v_slip`、
滑移标志、左右指接触位。实测（抓住梨时）：`Fn=37.7 N, Fasym=0.013, w=0.056 m`；
稳定搬运时 `v_slip≈0.007`（正确反映"没滑"）。

### 6.15.2 干净 A/B（同一份数据，只差 9 维触觉是否进模型）

数据：`dta-*`，0.06–0.18 m/s，四类各 50 局（专家 50/50、50/50、39/50、34/50），共 173 局。
两个模型同数据同超参：`act-ta-4c`（触觉，obs 61）vs `act-nota-4c`（无触觉，obs 52）。

| 0.08 m/s（四类各 6 局） | 有触觉 A | 无触觉 B |
| --- | --- | --- |
| 苹果 / 草莓 / 香蕉 / 梨 | 6/6、5/6、2/6、2/6 | 6/6、6/6、2/6、0/6 |
| **合计** | **15/24 = 62.5%** | **14/24 = 58.3%** |
| 峰值法向力（均值） | 40.1 / 26.4 / 25.0 / 10.8 N | 40.3 / 26.7 / 22.9 / 13.8 N |
| 累计滑移（均值） | 12.4 / 154.9 / 39.8 / 45.6 cm | 7.1 / 85.8 / 38.8 / 20.2 cm |
| 抓起后掉落 | 0/1/4/0 | 0/0/4/2 |

0.15 m/s：A 9/24 = 37.5%，B 15/24 = 62.5%（触觉更差）。

**结论：把触觉拼进 state 没有带来成功率或"无损"改善（+4pp 在噪声内，滑移反而更多，
0.15 明显更差）。**

### 6.15.3 为什么无效（三条，均有证据）

1. **夹爪力不可控**：`pd_ee_pose` 只有开/合两档，法向力由物体尺寸决定（实测 40 N / 26 N /
   10–14 N），策略无法"增力/减力"。而文献里触觉的收益主要来自**力作为动作通道**
   （FARM, arXiv:2510.13324）或**滑移触发的增力反射**（T-TO, arXiv:2010.01928）——
   这两条在这个动作空间里都不可用。
2. **没有失败样本**：示教全是成功轨迹，滑移帧占比 0.1–0.7%，滑移辅助头正样本≈0
   （训练日志 `slip 0.000`），学不到"滑移→补救"。
3. **管线自带逐列 z-score**：任何逐列仿射缩放都被归一化抵消（A 与 A2 的 val 完全相同
   0.0608），所以"无量纲化"在这套训练里是无效操作；触觉的价值只能来自**非线性交互**
   或**辅助监督**，而当前数据/动作空间两者都受限。

### 6.15.4 若要真正用上触觉（按性价比）

1. 换**力控夹爪**（动作里加目标夹持力），把 `Fn` 变成可调量 —— 这是文献里触觉起作用的前提；
2. 采**失败/滑移数据**（策略跑闭环、抓空/滑脱的片段），用触觉自动标滑移并训练辅助头；
3. 触觉单独编码成 token 再与视觉 cross-attention（arXiv:2504.13618、2606.06281），
   而不是拼到 state —— 但需要 2–3 倍数据量才看得出收益。

### 6.16.1 采策略闭环的失败片段（补上"示教无失败样本"的缺口）

`scripts/collect_slip.py`：跑带触觉的策略闭环，逐帧保存（`aux_only=True`，只参与滑移辅助损失）。

| 类 | 帧数 | 滑移帧（Fn>5N 且 v_slip>5cm/s） | 失败率 |

| 草莓 | 3359 | 698 | 2/6 |
| 香蕉 | 4601 | 181 | 4/6 |
| 梨 | 4441 | 1057 | 3/6 |
| **合计** | **15150** | **3313（21.9%）** | 11/24 |

### 6.16.2 滑移辅助头（aux 数据 2× 过采样）

`runs/act-ta-slip`（val 0.0553，优于 0.0608）。离线评估（2502 窗口，正样本 23.6%）：

```
滑移头 AUROC = 1.000 | 正样本平均概率 0.988 vs 负样本 0.001
阈值 0.5: 召回 0.99  误报 0.00
```

**这是退化结果，必须说清楚**：滑移标签由 `v_slip` 计算，而 `v_slip` 本身就在观测里（第 54 维），
模型直接读得到。所以这个头没有提供新信息。要有意义，标签必须算在**观测视野之外**
（例如 t+15 时刻的滑移），或把 `v_slip` 从输入里剔除。

### 6.16.3 触觉触发的补救（`--slip-guard`）：滑移降 24%，成功率不变

搬运中检测到滑移（Fn>3N 且 v_slip>5cm/s）→ 立即把搬运步长压到 1.2cm/步。
0.15 m/s、四类各 5 局：

| 配置 | 成功率 | 累计滑移（均值） | 抓起后掉落 |
| --- | --- | --- | --- |
| 无补救 | 7/20 = 35% | 34.0 cm | 5 |
| **`--slip-guard`** | 6/20 = 30% | **25.7 cm（−24%）** | 5 |

**滑移距离确实降了 1/4，但没有转化成成功率**——因为多数失败是"根本没抓住"（`carry=0`，
Fn=0），而不是"抓起来滑掉"；滑移补救对后者有效，对前者无能为力。

### 6.16.4 过程中修掉的一个严重 bug（值得记住）

为"无量纲化"把推理端触觉改成缩放值，但 `act-ta-4c` 是用**原始值**训练的 → 观测分布不匹配，
同一配置从 3/3 直接崩到 0/3。回滚为原始值后恢复 3/3。
**教训：训练/推理的特征变换必须由同一个常量控制；逐列 z-score 会抵消一切仿射缩放，
所以"归一化触觉"在这套管线里本来就是无效操作。**

### 6.16.5 结论

在「固定夹持力的平行夹爪 + 纯模仿学习」条件下：
- 触觉**作为观测**：成功率无收益（A/B 62.5% vs 58.3% @0.08）；
- 触觉**作为补救触发**：滑移距离 −24%，但成功率不涨（失败以"没抓住"为主）；
- 触觉**作为监督**：当前标签可由观测直接读出，退化。

要跨过去需要**力控**（把目标夹持力做成动作维度）或**接触前的预测性决策**
（在闭爪前用触觉历史判断"这一抓会不会滑"，而不是滑了再救）。

## 6.17 触觉迭代三：去泄漏的滑移预测 + 闭爪前重抓（v1.14）

### 6.17.1 修掉标签泄漏

原标签 = `max(slip[t+1..t+10])`，而 `v_slip` 就在观测里 → AUROC 1.0 是读数不是预测。
新标签 = **即将滑移的起始**：当前未滑、且 `t+5..t+20` 内会开始滑（5 帧盲区，强制预测）。
正样本比例 23.6% → 3.3%。

训练：`dta-*(173 局) + sdagger3-*(每类 4 局失败片段，4× 过采样)`，`--slip-head --slip-weight 1.0`
→ `runs/act-ta-onslip`（val 0.0502）。

### 6.17.2 留出集 AUROC（8 局失败片段，**未参与训练**）

| 滑移头 | AUROC | 正样本平均概率 | 负样本平均概率 |
| --- | --- | --- | --- |
| 旧（泄漏，t+1..t+10 max） | 0.611 | 0.460 | 0.328 |
| **新（onset，t+5..t+20 起始）** | **0.813** | 0.590 | 0.155 |

阈值 0.5 下：召回 0.59、误报 0.16、触发率 0.17。**这是"触觉作监督"第一次得到非退化的验证。**

### 6.17.3 闭爪前重抓（`--regrasp`）：类间互补，净收益随速度反转

触发条件：相位=下探、模型命令闭爪、滑移头概率 > 0.5 → 张开 → 下沉 2cm → 再闭。
0.08 / 0.15，四类各 8 局，对照组 `act-nota-4c`（同数据、无触觉、同种子）：

| 类 | 0.08 对照 | 0.08 重抓 | 0.15 对照 | 0.15 重抓 |
| --- | --- | --- | --- | --- |
| 苹果 | 8/8 | 4/8 | 5/8 | 3/8 |
| 草莓 | 8/8 | 5/8 | 8/8 | **0/8** |
| 香蕉 | 2/8 | **7/8** | 5/8 | **7/8** |
| 梨 | 0/8 | **6/8** | 1/8 | **4/8** |
| **合计** | 18/32 = 56.3% | **22/32 = 68.8%（+12.5pp）** | 19/32 = 59.4% | 14/32 = 43.8%（−15.6pp） |

累计滑移（0.08，均值）：重抓 79.5 cm vs 对照 48.7 cm —— 重抓要"张开再闭"，
张开瞬间物体会滑一段，所以滑移距离反而变大。

**解读**：滑移预测确实救回了"弱抓取"类（香蕉 2→7、梨 0→6），但在本来就稳的类上
（苹果/草莓，Fn 高、触发率也高）会误触发并破坏好抓取——0.15 草莓 8/8 → 0/8 就是典型。
即**触发器缺少"该不该干预"的判别**，而不是预测本身不行。

### 6.17.4 下一步（明确）

1. 触发门控：只在 `Fn` 低于类阈值、且 `slip_prob` 连续 N 帧高时才重抓（草莓 Fn≈26N 不该触发，
   而梨 Fn≈14N 该触发）——用触觉本身做门控，不需要新数据；
2. 或把"是否干预"也学出来（辅助头二分类：干预后成功率），标签用闭环 A/B 的结果；
3. 重抓改为"下沉 + 保持闭合"（不张开），避免张开瞬间的滑移。

## 6.18 为什么"草莓 8/8 却被重抓误触发"（v1.15 诊断）

问题：无触觉对照在 0.08/0.15 的草莓是 8/8，加上滑移触发的重抓后掉到 5/8、0/8。
如果抓得很稳，滑移头为什么还会报警？

**答案：草莓在成功搬运时一直在"微滑"，而我的规则把微滑当成了"即将失败"。**

`held` 帧内（物体贴着 TCP）的 `v_slip` 分布：

| 数据 | 类 | held 帧 | p50 | p90 | p99 |
| --- | --- | --- | --- | --- | --- |
| **成功示教** | 苹果 | 494 | 0.006 | 0.184 | 1.051 |
| **成功示教** | **草莓** | 553 | **0.124** | 0.173 | 0.991 |
| **成功示教** | 香蕉 | 660 | 0.045 | 0.182 | 0.705 |
| **成功示教** | 梨 | 618 | 0.007 | 0.033 | 0.688 |
| 失败闭环 | 苹果 | 2025 | 0.172 | 0.322 | 0.492 |
| 失败闭环 | 草莓 | 1090 | 0.152 | 0.233 | 0.501 |

也就是说：**草莓在成功抓取里中位滑移就有 12.4 cm/s**（圆、小、光滑，指面接触面小，
靠摩擦托着走时会持续微转/微滑），而我的触发阈值是 5 cm/s → 必然常触发 → 张开夹爪去"重抓"
→ 把一个本来能托住的水果主动放掉了。

阈值 5 cm/s 对苹果合适（成功时 p50=0.006），对草莓完全不合适——**触觉阈值必须按"类内成功分布"
标定，而不是全局常数**。

另外，尝试用"即将脱离夹爪"（held 由 1→0）做标签也失败：`held` 本身会抖
（成功示教的"即将脱离"率 5.7%，失败闭环 5.4%，不可分）。要可用，需要更稳的夹持判据
（双指接触 + 开口 < 物体宽度 + 连续 N 帧）。

**结论与修法**：
1. 触发门控改为 **类内相对阈值**（`v_slip > max(0.15, 3×该类成功示教 p50)`）+ 连续 2–3 帧；
   按上表，苹果/梨 ≈0.15–0.2，草莓 ≈0.37，香蕉 ≈0.15；
2. 或换成**"掉落预测"**而不是"滑移检测"：标签用"物体与 TCP 距离 > 夹爪半宽"的持续增大，
   并用双指接触稳定判据替代 `held`；
3. 干预动作也应更保守（下沉+保持闭合，而不是张开），避免张开瞬间真的掉。

| 触觉 token + 力通道（`act-tok-force`） | 0/3 |
| + 掉落头（`act-arch3`） | 0/3 |

**结论：把触觉塞进策略（无论拼 state 还是独立 token）都会拖累闭环；力动作通道进一步恶化。**
训练/验证 loss 都很好（train 0.0027），但闭环行为崩（`carry` 不释放、掉落头饱和）——
又一次印证"离线指标 ≠ 闭环可用"。

### 6.20.2 但把掉落预测拆成独立模块，效果很好

`scripts/train_drop_predictor.py`：轻量 MLP（48 维输入 = 5 帧×9 触觉 + 物体距离/是否贴住/带速），
主策略完全不参与。

| 预测器 | 留出集 AUROC | 召回（阈值 0.5） | 误报 |
| --- | --- | --- | --- |
| 策略内掉落头（6.95M 里的一部分） | 0.779 | 0.53 | 0.19 |
| **独立 DropNet（~20k 参数）** | **0.937** | **0.89** | 0.15 |

留出方式：pear/banana 的失败片段整段不进训练（7 个 ep、~2.4k 帧）。

### 6.20.3 接回部署：中性

`act-wide-4c` + 独立预测器触发重抓（阈值 0.7 保守），0.08 四类各 8 局：

| 配置 | 苹果 | 草莓 | 香蕉 | 梨 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 基线 | 8/8 | 8/8 | 8/8 | 4/8 | 28/32 = 87.5% |
| **+ 掉落触发重抓** | 8/8 | 7/8 | 8/8 | 4/8 | 27/32 = 84.4% |

触发几乎不误伤（阈值高），但也**没带来收益**——因为剩下的失败不是"抓起来掉了"，
而是"根本没抓住"（梨 4/8 中的 4 次是 `carry=0`）。掉落预测再准也救不了没抓到的。

### 6.20.4 三条改动的最终判定

| 改动 | 预测能力 | 闭环收益 | 结论 |
| --- | --- | --- | --- |
| ① 触觉独立 token | 与拼 state 相当 | **负**（3/3→1/3） | 不采用 |
| ② 力作为动作通道 | — | **负**（0/3） | 不采用（需真正力控夹爪） |
| ③ 掉落预测触发 | **AUROC 0.937** | 中性（±1 局） | 保留为独立模块/监控 |

**部署仍为 `act-wide-4c`：0.08 87.5%、0.15 96.9%。**

## 6.21 宽度设定点（LeTac 式位置等价力控）：力能调，但调下来就抓不住（v1.18）

### 6.21.1 标定（从 170 局带触觉示教统计"抓持帧"）

| 类 | 抓持时开口 w*（中位） | 抓持时 Fn（中位） |
| --- | --- | --- |
| 苹果 | 0.062 m | 40.3 N |
| 草莓 | 0.034 m | 26.5 N |
| 香蕉 | 0.044 m | 27.3 N |
| 梨 | 0.068 m | 43.1 N |

（注：`qpos` 在 obs 里是 `[7:16]`，手指是 `obs[14]+obs[15]`——一开始用错了列，算出来是负数。）

### 6.21.2 位置确实能改力（静止夹持）

`gripper` 指令 g 与空载开口近似线性：`gap ≈ 0.030 + 0.050·g`。把 g 当"目标开口"用，
夹住苹果时实测：

| g | 实际开口 | Fn | 静止夹住 |
| --- | --- | --- | --- |
| −1.0 | 0.000 | 1.3 N | ✗（水果被挤出） |
| +0.1 | 0.055 | 20.1 N | ✓ |
| +0.3 | 0.064 | 10.4 N | ✓ |

**所以"位置等价力控"在我们仿真里是可行的：40 N 可以压到 10–20 N。**

### 6.21.3 但闭环搬运时，只有"夹到底"能活

用宽度设定点做闭环（0.08 m/s 苹果 5 局）：

| 闭合指令 | 峰值 Fn | 成功率 |
| --- | --- | --- |
| −1.0（基线，闭到底） | 40.3 N | **5/5** |
| −0.5 | 28.5 N | 0/5 |
| −0.3 | 23.8 N | 0/5 |
| 0.0 | 16.7 N | 0/5 |
| +0.1 | 14.4 N | 0/5 |
| +0.2 | 12.0 N | 0/5 |

**结论：在这个仿真里，"能搬住"的最小夹持力就在 ~40 N 附近。** 一旦降到 28 N 以下，
水果在搬运中全部脱落——不管静力上是否够（2 N 重力 vs 10+ N 摩擦），
实际是**接触几何**变差（半闭时只有指尖接触、摩擦锥小）。

所以论文里"轻柔抓取/力上限"的思路，在本仿真**没有可用窗口**：
不是我们不会调力，而是**调下来就抓不住**。要实现"无损抓取"，需要改物理侧
（软指/更高摩擦接触面），而不是控制侧。

### 6.21.4 对"融合触觉"的最终判断

| 触觉用法 | 结果 |
| --- | --- |
| 作观测（拼 state / 独立 token） | 负（62.5% vs 58.3%；3/3→1/3） |
| 作动作通道（第 5 维目标力） | 负（0/3） |
| 作监督（滑移/掉落预测） | **正**（独立 MLP 留出 AUROC 0.937） |
| 作闭环补救（降速/重抓/验证门） | 中性（±1 局） |
| 作力控（宽度设定点） | 力可调但**调下来就抓不住**（28 N 即 0/5） |

**根因**：本任务的失败集中在「接触前对准」和「夹爪物理」，而不是「触点信息不足」。
在只有位置权限 + 硬指 + 低摩擦的设定下，触觉能给的是"监控/告警"，给不了"更好的抓取"。

## 6.22 对准与夹爪物理：渲染截图定位到「夹在果尖」（v1.19）

### 6.22.1 对准不是瓶颈

四类失败局实测：TCP 与水果的**最近距离 0.2–1.0 cm**（dx/dy/dz 均 <1cm）。
策略的接近/预瞄已经很准，不是"没对上"。

### 6.22.2 截图暴露真正问题：只夹到梨的顶端

在闭爪瞬间渲染并放大（`/tmp/opencode/pear_close_zoom.png`）：
两指只接触梨**顶部一小块**（指尖接触），梨的果身在两指下方——抓取点太深（TCP 到果心）。

**扫描抓取高度（专家，0.08，10 局）**：

| TCP 高度偏移 | 成功率 |
| --- | --- |
| 0（原来，果心） | 6/10 |
| **抬高 1 cm** | **9/10** |
| **抬高 2 cm** | **9/10** |
| 抬高 3 cm | 4/10 |

固化到专家：`pear_extra_depth = −0.015`，重采梨示教 → **32/50 → 37/40（92.5%）**。

### 6.22.3 策略侧：重训不迁移，执行层偏置才有效

| 方案 | 0.08 梨 |
| --- | --- |
| 基线 `act-wide-4c` | 4/8 = 50% |
| 用修正示教重训（含触觉 state） | 0/8（且苹果 8/8→6/8） |
| 用修正示教重训（`--no-tactile`） | 0/8（香蕉 8/8→0/8，训练不稳） |
| 梨单类模型（37 条修正示教） | 1/10 |
| **基线 + 执行层 z 偏置 +1.5cm（仅梨）** | **5/8 = 62.5%** |

结论：策略的 z 精度约 ±1cm，**重现不了 1.5cm 的抬高**；把它放到执行层（按类的工具偏置）
才有收益。`--z-bias 0.015` 只对梨开（香蕉加偏置会 8/8→0/8）。

### 6.22.4 夹爪物理的两次尝试（均无效/有耦合）

| 方案 | 结果 |
| --- | --- |
| 水果材质摩擦 ×2/×4 | 梨 6→6→8/10，但**香蕉 10/10→0/10**（水果-传送带摩擦同时变大，水果不再被带面驱动） |
| 夹爪侧软指等效 `pad_mu`（黏性摩擦上限 μ·Fn） | 梨 6/10、策略 4/8，**完全无变化** |

→ 摩擦不是主要矛盾；**接触几何（夹在果身还是果尖）才是**。

## 6.5 已定位的模型缺陷（v0.6 诊断）

用 20 组对照实验（`/tmp/vision_diag/`）定位到两个训练侧问题：

1. **动作头有"悬停不动点"**：z 用绝对值回归 + 示教里悬停帧占多数，闭环目标 z 平均比水果高 7.7 cm，
   进入抓取区后只有 2% 的帧低于 +3 cm。修复方向：z 改为预测 **Δz**（相对当前 TCP），或对下探帧过采样。
2. **夹爪头类别极不平衡**：闭合帧仅占 18%，BCE 无 pos_weight，模型在 600 个专家帧上从未预测闭合。
   修复方向：`pos_weight≈4.5` + `grip_head.bias` 初始化到 logit(0.18)。

当前的工程绕法是：**夹爪与近距伺服改用几何判据**（d<0.05 且水果在抓取区），模型只负责远距目标与水果选择。
这也是 `docs/gripper-timing.md` 的结论：1 bit 的"何时闭爪"不该交给回归头。

```bash
    --episodes 8 --belt 0.08 --hand-open 0.0 --hand-close 0.30 --grasp-depth 0.0
```

### 6.25.4 截图诊断：手停在果子上方，"手指没有包住果子"

在 `CLOSE→CARRY` 瞬间渲染并放大（`data/fruitsort/eval/allegro_close_zoom.png`）：
Allegro 的手掌在苹果**上方偏后**，四指朝下但没有包住果子——所以 `is_grasping`
（指尖有接触力）为真，一抬升水果就滑脱。

参数扫描（每组合 1 局，苹果）：

| 维度 | 试过 | 结果 |
| --- | --- | --- |
| 手指张开/闭合 | (0,0.15) (0,0.35) (−0.5,0.3) (−1,0.4) (0,0.3) | 全部 0/1；4 组能进 CARRY 但 <20 步滑脱 |
| 抓取深度 `--grasp-depth` | −0.04 / −0.02 / 0 / +0.02 / +0.03 | 全部 0/1 |
| 侧向抓取 `--grasp-tilt` | ±1.5 rad | 1.5 → 0/1；−1.5 能进 CARRY 但滑脱 |
| D'Claw 同流程 | 开合 + 深度 + 倾角 | 到 LIFT 但接触力 0（从未夹住） |

根因是**几何**，不是控制：

- 苹果中心距带面只有 ~3 cm（半径 3–4 cm），手指最多只能进到果心下方 3 cm；
- Allegro 指尖到掌心 ~10 cm、D'Claw 腕到指尖 ~29 cm，
  两种手都把"果子放在指内"的空间需求变成了"手指必须穿进传送带"；
- 平行夹爪之所以能抓，是因为它的两片指垫只有 4 cm 长，能从两侧夹住果身。

## 6.26 连续作业（传送带不停、间隔随机、尺寸随机）（v1.23）

### 6.26.1 新场景 `FruitSortStream-v1`

`FruitSort-v1` 每种水果只有一个 actor、一次只放一颗，"成功"是"四类全入框"。
连续作业需要不同的机制，因此新增 `src/fruitsort/sim/tasks/fruit_stream.py`：

| 维度 | 做法 |
| --- | --- |
| 多件在飞 | 每类 3 个 slot（默认共 12 件），上料/回收循环使用 |
| 随机间隔 | 单一下料流，相邻两件间距 `U(gap_min, gap_max)`（默认 0.6–1.2 m） |
| 随机类别 | 每次上料从"当前有空 slot 的类别"里随机抽 |
| 随机尺寸 | 每个 slot 创建时抽 `U(0.85, 1.15)` 缩放（果径 ±15%） |
| 按件统计 | spawned / delivered / dropped / missed / picked + 每件事件时间戳 |
| 观测保真 | 保证"四类都在场"（某类空了立刻补一件），否则 `build_obs` 会出现 `active=0` 的分布外输入 |

评测脚本 `scripts/stream_eval.py` 还带一个**目标选择层**（策略只会"抓某类的最近一件"，
抓哪件、什么时候换由这一层决定），以及 `--record` 可以把专家在流里的成功片段录成训练数据。

### 6.26.2 基线：现有模型在连续作业下明显失效

条件：0.08 m/s，尺寸 ±15%，30 Hz，单臂，单局 120 s；两种喂料率各测一轮
（间隔下限/上限换算成到达率：2.0–3.0 m ≈ 每 25–38 s 一件；0.6–1.2 m ≈ 每 7–15 s 一件）。

| 喂料 | 策略 | 送达/上料 | 成功率 | 吞吐 |
| --- | --- | --- | --- | --- |
| **2.0–3.0 m**（≈3.5 件/min，可持续） | `act-wide-4c`（部署模型） | 1/7 | **14.3%** | 0.5 件/min |
| 同上 | `act-stream`（微调后） | 0/7 | 0% | 0 |
| 同上 | **规则专家** | **6/7** | **85.7%** | **3.0 件/min** |
| **0.6–1.2 m**（≈12 件/min，超载） | `act-wide-4c` | 2/12 | 16.7% | 1.0 件/min |
| 同上 | `act-stream` | 1/11 | 8.3% | 0.5 件/min |
| 同上 | **规则专家** | **9/13** | **69.2%** | **4.5 件/min** |

数据：`runs/2026-11-21-stream-{act,actstream,scripted}-*/metrics.json`。

**同一场景、同一目标选择层、同一喂料率：专家 85.7% / 69.2%，模型 14.3% / 16.7%。**
所以场景、调度、判据都是可行的，**瓶颈在模型本身**。

### 6.26.3 失败机理（逐步 trace）

在低喂料、可控条件下抓一段 trace（30 Hz，Apple 为目标）：

```
t=1080 目标苹果=-0.60  TCP=(0.00, 0.01, 0.56)  action=(0.529, 0.013, 0.601) phase=1 张开
t=1110 目标苹果=-0.51  TCP=(-0.01,0.03, 0.62)  action=(0.550, 0.025, 0.673) phase=1 张开
t=1140 目标苹果=-0.43  TCP=(-0.01,0.03, 0.62)  action=(0.550, 0.025, 0.673)   ← 完全冻结
t=1170 目标苹果=-0.34  TCP=(-0.01,0.03, 0.62)  action=(0.550, 0.025, 0.673)   ← 完全冻结
```

- 模型在"接近"相位输出的增量是**向上偏后**（+0.06 x、+0.12 z），
  而执行器的残差反馈 `fb=0.5` 把目标往水果拉；水果已经离得 0.4 m，
  `corr` 被截断在 ±0.15 → 反馈量饱和成常数。
- **两个力正好抵消**，TCP 与动作逐帧完全相同（不是抖动，是精确不变），
  水果被传送带带走 → 判漏过。
- 换目标、硬复位关节、减少场上件数（slots=1）、只用单类、回 home 等待，
  都改变不了"1 件之后就冻结"的模式 → 不是调度问题，是模型在
  "多件、随机布局、随机尺寸"下**没有学会接近**。

### 6.26.4 尝试一：用连续流数据微调（未成功）

1. `scripts/stream_eval.py --record` 把专家在流里的**成功片段**录成训练数据
   （与 `record_demos.py` 完全同格式：49 维状态 + 双路 128² 图像 + 4 维绝对目标）：
   0.08 m/s ×2 种子 + 0.15 m/s，共 **102 条**；
2. `train_act.py --init runs/act-wide-4c/ckpt.pt` 微调 30 epoch（混入原 `dwt-*` 防遗忘）。

| 指标 | `act-wide-4c` | `act-stream`（微调后） |
| --- | --- | --- |
| 连续作业 @3.5 件/min（间隔 2–3 m） | 1/7 = 14.3% | **0/7 = 0%** |
| 连续作业 @12 件/min（间隔 0.6–1.2 m） | 2/12 = 16.7%，1.0 件/min | **1/11 = 8.3%，0.5 件/min** |
| 单发评测 apple（8 局 0.08） | 8/8 = 100% | **2/4 = 50%（退化）** |
| 单发评测 banana | 8/8 | 4/4 |

**结论：102 条连续流示教不足以把"单发策略"改成"队列策略"**，而且微调还损伤了
单发能力（catastrophic forgetting）。瓶颈不在数据格式，而在于：
- 连续作业里"从料框上方继续接管"的状态几乎没在训练集中出现；
- 场上有 4–12 件、位置/尺寸随机，状态分布远比训练集宽。

### 6.26.5 尝试二：把状态观测重映射回训练布局（也未成功）

模型的状态观测里有四类的绝对位置，而训练时它们固定在 `spawn_x − 0.45·i` 的布局上。
于是试了"把**非目标类**按训练布局摆到目标 ± 0.45·Δi 的替身位置"（`--in-dist-obs`，
只改观测、不改真实物理）：

| 配置 | 送达/上料 | 成功率 |
| --- | --- | --- |
| `act-wide-4c` + 真实布局 | 2/12 | 16.7% |
| `act-wide-4c` + 训练布局重映射 | 1/12 | 8.3% |

没有改善 → 说明不是"非目标类位置"的问题，图像输入与"从料框上方继续接管"的动力学
才是主因，只能在数据侧解决。

### 6.26.6 尝试三：连续流里做 DAgger（**结果：有害**）

做法（`scripts/stream_dagger.py`）：**模型驱动 rollout**，每一步用规则专家对**当前状态**
给出动作标签（`ScriptedSorter.last_target`，与训练标签同格式），按"目标件"切段保存。

| 项 | 值 |
| --- | --- |
| 采集片段 | 28 段 / 8307 帧（5 个采集器 × 300–360 s，不同种子/带速/间距） |
| 微调 | `--init runs/act-wide-4c`，25 epoch，lr 2e-5，混入流示教 102 段 + `dwt-*`（aux×2） |
| 验证 | val 0.2532（**注**：修掉了"验证集为空"的 bug，见下） |

| 评测 | `act-wide-4c` | `act-dagger`（DAgger 微调） |
| --- | --- | --- |
| 连续 @0.6–1.2 m | 2/12 = 16.7% | **0/14 = 0%** |
| 连续 @2–3 m | 1/7 = 14.3% | **0/7 = 0%** |
| 单发 apple（4 局） | 8/8（历史） | **0/4 = 0%** |
| 单发 banana（4 局） | 8/8（历史） | **1/4 = 25%** |

**DAgger 不但没救活连续作业，还把单发能力打崩了。** 两个原因都能量化：

1. **标签在这些状态上没有意义**：模型会一直悬停到水果越过可抓窗口（x>0.3），
   此时专家的 FSM 仍给出"去拦截点"的绝对目标——方向朝后/朝上，幅度很大。
   这类样本占了 DAgger 数据的大头，把策略往错误方向拉。
2. **数据量差了两个数量级**：目标是 500+ 段，实际只采到 28 段。采集成本：
   60 s 仿真 ≈ 2–4 min 墙钟（双相机渲染 + 模型推理），且模型吞吐低、能"触发"的件数少
   （≈3–6 段/min，多数时间一件都抓不到）。

> 附带修掉一个训练脚本 bug：`--aux-data` 存在时，留出的验证 episode 全是 aux（被排除），
> `val` 恒为 0 → best-ckpt 选择失效。现在只从主数据留验证集（6.26.6 的 val 0.2532 是真实的）。

### 6.26.7 尝试四：过滤"逃逸态"标签 + 裁剪到部署步长（仍然有害）

针对 6.26.6 的两个疑点各做一次修正，用**已有数据**重训（`scripts/filter_dagger.py`）：

- 只保留目标水果在可抓窗口 `x∈[−0.62, 0.22]` 的帧：8307 → 6487 帧（22% 被丢）；
- 标签裁剪到部署步长 `±0.06 m`（DAgger 里专家目标可能距当前 TCP 0.4 m，
  直接当标签会让位置头学到不可执行的跳变）。

微调配方同上（`--init act-wide-4c`、25 epoch、lr 2e-5、混入流示教 + `dwt` aux×2），
best val 0.2641。结果：

| 评测 | `act-wide-4c` | `act-dagger` | `act-dagger-filt` |
| --- | --- | --- | --- |
| 连续 @0.6–1.2 m | 2/12 = 16.7% | 0/14 | **0/9** |
| 连续 @2–3 m | 1/7 = 14.3% | 0/7 | — |
| 单发 apple 4 局 | **8/8** | 0/4 | 0/4 |
| 单发 banana 4 局 | **8/8** | 1/4 | 0/4 |

结论：**问题不在标签过滤，而在"小样本微调本身"**——25 epoch 的微调无论数据怎么筛，
都会把原策略的单发能力打崩（8/8 → 0/4）。这条路线在当前数据规模下不可行。

### 6.26.8 尝试五：冻结主干 + 只训适配头（仍未保住单发）

按"避免灾难性遗忘"的标准做法：**冻结视觉编码器与 Transformer 编码器，只训 decoder + 头**
（3.69M / 6.88M 可训练），`--init act-wide-4c`，5 epoch，lr 3e-5。

| 评测 | `act-wide-4c` | 全量微调(`act-dagger-filt`) | **冻结主干(`act-adapter`)** |
| --- | --- | --- | --- |
| 单发 apple 4 局 | **8/8** | 0/4 | **0/4** |
| 单发 banana 4 局 | **8/8** | 0/4 | **0/4** |

**冻结主干也没能保住单发能力** → 灾难性遗忘不是主因，问题在**新数据的监督信号与原始训练设定
不一致**。这一轮把两个可疑点排除掉了：

- 归一化器复用（`--reuse-norm`）：xyz 损失从 0.7 爆到 4.8e5（发散），不是解法；
- 标签裁剪/逃逸态过滤（6.26.7）：也没有改善。

仍在嫌疑名单上、但本轮没时间验证的：
- 采集数据里 `obs` 只有 49 维（无触觉），而原 `dwt` 数据带触觉列，
  `ImageDemoDataset` 的相位/未来特征对列布局敏感（已确认 `force_label` 分支有 `>=58` 保护，
  但 `use_phase` 的相位标签由**动作序列**推导，两套数据的动作节奏不同会影响相位标注）；
- `--delta-actions` 的 `delta_clip=0.06` 与采集时的执行步长是否一致。

### 6.26.9 尝试六：**从零**在连续流数据上训练（决定性诊断，仍失败）

为了区分"数据不可学"与"微调有问题"，直接从零（不 `--init`）在
`stream-* + dagger-filt`（约 130 段）上训练 20 epoch：

```
epoch  19 train 0.0438 (xyz 0.0305 grip 0.0033 kl 0.0026 ph 0.0084) val 20.3175 (ph 0.8692)
```

**验证损失是训练损失的 ~400 倍**（20.3 vs 0.044）——这不是过拟合，而是
**验证集（留出的连续流 episode）与训练部分的映射关系根本不同**：模型能背下训练片段，
却学不到"多件 + 随机布局 + 队列上下文"下的状态→动作映射。

评测：单发 apple **0/4**，连续 @0.6–1.2 m **0/N**。

**这才是真正的瓶颈**：连续流数据在当前"回归式 ACT（chunk 回归 + 小样本）"下不可学，
而不是微调配方。把六次尝试放在一起看：

| # | 尝试 | 单发 apple | 连续作业 |
| --- | --- | --- | --- |
| – | `act-wide-4c`（基线） | 8/8 | 14–17% |
| 1 | 流示教微调 | 2/4 | 8.3% |
| 2 | 观测按训练布局重映射 | — | 8.3% |
| 3 | 连续流 DAgger（28 段） | 0/4 | 0% |
| 4 | DAgger + 逃逸态过滤 + 标签裁剪 | 0/4 | 0% |
| 5 | 冻结主干只训 decoder（适配器） | 0/4 | — |
| 6 | **从零**训练（130 段连续流数据） | 0/4 | 0% |

### 6.26.10 可学性门槛 + 逐列标签排查（v1.25.1，结论：数据可学，瓶颈是泛化/复合误差）

按"先过门槛再扩数据"的流程做的三件事（都用 6 段连续流示教，关增强/dropout）：

**(1) 可学性门槛（v1.25.2 修正：此前用 episode 级留出，val 天然不可比）**

关键：6 段数据做 **episode 级**留出时，val 是"另外两个 episode"，测的是跨 episode 泛化，
不是"映射能否拟合"。改为 **`--window-val`（同一批 episode 的窗口随机切分）**，
150–200 epoch：

| 数据 | train | **val（窗口级）** | val（旧：episode 级） |
| --- | --- | --- | --- |
| `dwt`（对照） | 0.0008 | **0.0256** | 0.73 |
| `stream`（连续流） | 0.0036 | **0.0444** | 10.03 |

→ **train 与 val 都 < 0.05，门槛真正通过**：`state→action` 映射本身**可以拟合**，
之前的 val=10 是"6 段做 episode 级留出"造成的假象（训练/验证 episode 的取件相位完全不同）。
所以不是"数据不可学"，也不是标签 bug；剩下的问题是**跨 episode 泛化 + 闭环复合误差**。

**(2) 逐列标签排查**（评审要求）

| 检查项 | dwt | stream | 结论 |
| --- | --- | --- | --- |
| obs 列数 | 58（49+9 触觉） | 49 | `--no-tactile` 两者都裁到 49，一致 |
| 动作增量 \|Δ\| 均值 | 0.030 | 0.033 | 一致 |
| 闭爪帧比例 | 0.46 | 0.54 | 合理（连续流里抓取占比更高） |
| 带速（obs[16]） | 0.127 | 0.080 | 各自记录，无异常 |
| 相位标签 `episode_phase` | 由 obs/act 计算 | 同 | 列索引 17+8j+2 在 49 列布局下正确 |

→ **没有找到标签 bug**。

**(3) 数据量 → 泛化 学习曲线**（只用流数据，40 epoch，no-cvae/no-aug）

| 训练段数 | train | 最佳 val |
| --- | --- | --- |
| 6 | 0.087 | 2.775 |
| 30 | 0.016 | **0.203** |
| 102 | 0.012 | 0.270 |

val 从 2.78 降到 0.20（6→30 段，13 倍改善）后进入平台 → **泛化确实受数据量限制**；
同时也说明之前"混入 `dwt` aux"的配方是错的（val 20 vs 纯流 0.27，差 70 倍）：
单发固定布局的 `dwt` 与队列化的 stream 数据**分布冲突**。

**(4) 但离线好 ≠ 闭环好**

用纯流数据从零训练的模型（val 0.27）闭环复评：

| 模型 | 连续 @0.6–1.2 m | 单发 apple |
| --- | --- | --- |
| `act-wide-4c` | 2/14 = 16.7% | **8/8** |
| 纯流从零训练 | 2/13 = 15.4% | 2/4 |
| 专家 | **9/14 = 69.2%** | 8/8 |

val 0.27 对应每步增量误差 ~1.5 cm，但闭环仍然崩——这是典型的**复合误差 / causal confusion**：
模型在专家状态上很准，一旦进入自己的状态分布就漂移。**这正是 DAgger 要解决的问题**，
而本轮的 DAgger 数据被"逃逸态标签"污染、且用了微调（会打崩主干），两条都踩了坑。

### 6.26.11 尝试八：DAgger 数据 + **从零训练**（非微调，v1.25.2）

按修正后的流程：`filter_dagger.py` 只保留有效窗口、标签裁剪到 ±0.06，
合并 `dagger-all`（44 段 / 8807 帧）+ 流示教 102 段，**从零**训练 60 epoch
（不 `--init`，避免微调打崩主干），best val 0.266：

| 模型 | 连续 @0.6–1.2 m | 单发 apple |
| --- | --- | --- |
| `act-wide-4c`（部署） | **2/14 = 16.7%** | **8/8** |
| 纯流从零（无 DAgger） | 2/13 = 15.4% | 2/4 |
| **DAgger 从零** | **0/14 = 0%** | **0/4** |
| 规则专家 | **9/14 = 69.2%** | 8/8 |

**加入 DAgger 数据反而更差** → 即便过滤+裁剪，DAgger 标签的质量仍不足以训练，
或者 44 段（≈8.8k 帧）在 ~150 段的混合数据里占比太低、噪声占比太高。

### 6.26.12 尝试九：换成 **Flow Matching**（rectified flow）策略（v1.26）

评审建议换策略类。实现方式（复用现有编码器/decoder，runner 接口不变）：

- `ActConfig.use_flow`；decoder 隐状态 `h` 不变，**xyz 用流采样**：
  `x0~N(0,1)`，`x_t=(1−t)x0+t·x1`，回归速度 `v=x1−x0`，推理用 8 步欧拉积分；
- 夹爪仍用 `grip_head` 的 logit（部署端 `grip_ema`/阈值逻辑不变）；
- `train_act.py --flow`：损失 = 速度 MSE + 夹爪 BCE + 相位 CE；
- `ActPolicy.forward` 在 `use_flow` 时自动走采样，`ActPureRunner` 无需改动。

从零训练 60 epoch（stream 102 段 + dagger-all 44 段，val 10.47）：

| 模型 | 连续 @0.6–1.2 m | 单发 apple |
| --- | --- | --- |

| ACT 从零（纯流） | 2/13 = 15.4% | 2/4 |
| **Flow 从零** | **0/14 = 0%** | **0/4** |
| 规则专家 | **9/14 = 69.2%** | 8/8 |

**换策略类没有解决问题**：flow 在同样数据上比回归 ACT 更差。

### 6.26.13 **重要更正：此前"连续作业 0–17%"主要是评测链路的 bug（v1.27）**

定位过程：部署模型 `act-wide-4c` 在**标准单发场景是 8/8**，但在连续流里只有 16.7%。
把同一个模型放进"稀疏流"（每类 1 个 slot、间隔 3–4 m）依然是 16.7% —— 说明不是模型，
而是评测链路。根因：

> `StreamController._repoint()` 只更新"当前有在飞件"的类别；
> **某类没有在飞件时，`u.fruit_actors[kind]` 仍然指向被停到场外（z=−5）的那个 actor**，
> `build_obs` 于是把 z=−5 的"水果"喂给模型 → 分布外观测 → 策略完全冻结
> （这正好解释了所有 trace 里"TCP 逐帧不变"的现象）。

修法：缺类时给一个**合理替身**（刚上料的位姿：`stream_x, 0, belt_top + half_height`，
速度 = 带速），已同时修在 `stream_eval.py` 与 `stream_dagger.py`。

**修正后的任务级对照（0.08 m/s，120 s/局，间隔/尺寸随机，修复链路）**

| 喂料 | 策略 | 送达/上料 | 成功率 | 吞吐 |
| --- | --- | --- | --- | --- |
| **3–4 m（≈2–3 件/min，可持续）** | `act-wide-4c` | **4/6** | **66.7%** | 2.0 件/min |
| 同上 | 规则专家 | 5/6 | **83.3%** | 2.5 件/min |
| **0.6–1.2 m（≈12 件/min，超载）** | `act-wide-4c` | 3/14 | **23.1%** | 1.5 件/min |
| 同上 | 规则专家 | 10/14 | **76.9%** | 5.0 件/min |

- **模型确实可以连续作业**：在可持续喂料下 66.7%，与专家（83.3%）差 17 个百分点；
- 超载（12 件/min）时掉到 23.1% —— 这是**产能**问题（单臂 ~4–6 件/min），不是"完全不能用"；
- 之前 6.26.2–6.26.12 里所有"0–17%"的数字都含这个 bug，**应以上表为准**；
  "微调打崩单发 8/8→0/4"的结论**不受影响**（单发评测不走这套 `_repoint`）。

### 6.26.16 A/B 结论：**训练脚本没问题，问题在 stream 录制数据**（v1.29）

**结论**：同一脚本从零训练 dwt 就能把 apple 复现到 100% → **训练脚本没问题**；

最可疑的差异已定位并做了修正尝试：录制时缺类用的是"ghost 观测"（状态里有、图像里没有），
属于**图文不一致**。为此新增：

- `always_stock`（录制时缺类立刻补货）+ 只录"四类都在场"的帧（`stream_eval --record`）；
- 采集产出随之降到 **5–7 段/300 s 仿真**（要保证四类同时在场，喂料必须密）；
  本轮共采到 33 段干净数据，不足以重训出结论（需要 ≥100 段）。

### 6.26.17 干净数据重训（51 段）：离线 val 0.058，但**首步方向就是错的**（v1.30）

用 `always_stock` + 只录"四类齐全"帧，共采到 **51 段**（`clean-a…l`，受产量限制，
约 6 段/20 min 仿真；同时修掉 `max_episode_steps=7200`（30 Hz 下只有 240 s）导致的采集截断）。

从零训练 40 epoch：**val 0.0575 / train 0.0075**（史上最好的离线指标）。

但闭环仍然 0：单发 apple/banana 0/4、0/4；流场景稀疏 0/6（含 1 次掉落）。

**决定性诊断（同一起点、同一帧，直接看模型原始输出）**

| 模型 | 第 1 步 Δxyz | 需要方向 | 预测相位 |
| --- | --- | --- | --- |
| `act-wide-4c`（部署，dwt） | (−4.8, +5.6, −2.6) cm | (−55, +34, −17) cm | 0 接近 ✓ |
| `act-clean`（stream 录制） | **(+13.2, +9.6, +21.0)** cm | 同上 | **1 下探 ✗** |

→ 新数据模型在部署状态下的**输出方向是反的（向上偏后）**、且首帧就误判为"下探"。
离线 val 好只说明它拟合了**录制数据里的状态**，而那些状态与部署时 runner 喂进去的状态**不是同一个分布**
（录制时非目标类指向"最近的一件/ghost"，部署时指向最近件或 ghost，二者的 `fruit_actors` 布局、
目标切换时刻、相位标注都不同）。

**结论：问题不在模型结构/训练量，而在"录制协议的观测构造"与"部署 runner 的观测构造"不一致。**
这也是为什么同一脚本训练 dwt 数据（录制与部署都在 `FruitSort-v1`、布局一致）就能到 apple 4/4。

| --- | --- | --- | --- | --- | --- |
| `act-425` | 8/8 | 0/8 | ✗ | 0/6 | 0/14 |
| `act-425-dg`（失败状态 DAgger） | 0/8 | — | ✗ | 1/5 | 1/12 |
| **`act-noisy`（噪声 1 cm）** | **8/8** | **7/8** | **✓ 首次** | 1/6 (16.7%) | 1/12 (9.1%) |
| `act-wide-4c`（部署） | 8/8 | 8/8 | ✓ | **66.7%** | 23.1% |

**关键收获**：`--noise 0.01` 的小扰动数据**同时修好了 banana**（0/8 → 7/8）——
之前 15 次尝试（混训/专科/DAgger 失败状态/执行层补救）都没做到。
机理：噪声让"接近成功轨迹"的状态也带上专家标签，等价于在专家吸引域内做 DAgger，
而收集模型失败状态会把策略拉向失败分布（6.26.22 的负结果）。

**但连续作业仍是 16.7%**（分项：apple 1/2、其余 0），而单发 apple 是 8/8
→ 再次证明**"会抓"与"在队列里会抓"是两件事**，后者需要**流场景里**的 on-policy 数据。

为此已在 `stream_eval.py` 增加 `--noise`（录制时扰动专家动作）：
下一步直接用 `--policy scripted --record --noise 0.01` 在流里采"专家附近"的数据。

### 6.26.25 流场景"专家附近"数据（14 段）：连续无改善，且稀释 banana（v1.38）

用新增的 `--noise 0.01` 在流场景采"专家附近"数据：3 × 300 s 仿真 → **仅 14 段**
（"四类齐全"过滤 + 缺类切段，产量 ~6 段/300 s 仿真），`--aux-boost 8` 混入 425+noisy 训练 15 epoch：

| 模型 | 单发 apple | 单发 banana | 连续 3–4 m | 连续 0.6–1.2 m |
| --- | --- | --- | --- | --- |
| `act-noisy`（无流数据） | **8/8** | **7/8** | 1/6 = 16.7% | 1/12 = 9.1% |
| `act-snoisy`（+14 段流数据） | 8/8 | **3/8（被稀释）** | 1/6 = 16.7% | 1/12 = 8.3% |
| `act-wide-4c`（部署） | 8/8 | 8/8 | **66.7%** | 23.1% |

→ 14 段（约 3000 帧）的流上下文数据**太少**，既没提升连续，还稀释了 banana（7/8 → 3/8）。

**量级估算**：流录制受"四类齐全"限制，约 6 段/300 s 仿真 ≈ 6 段/7 min 墙钟（3 路并行）；
要到部署模型那种流上下文覆盖（其训练用 `--aux-data dagger-*`，数万帧），需要 **≥100 段流数据**
≈ 1.5–2 h 墙钟采集，再训练 40 min。这是本会话之外的工作量。

### 6.26.26 **连续作业首次超过部署模型**（v1.39）

关键突破在**采集吞吐**：此前"只录四类齐全帧"的过滤把 35 件/120 s 的送达砍成 4 段。
部署端本来也会喂 ghost 观测（缺类时），因此允许 ghost 帧是**与部署一致**的做法——
产量从 4 段/60 s 提到 **35 段/120 s（≈17×）**。

采集：`stream_eval --policy scripted --noise 0.01 --allow-ghost-frames`，3 × 300 s
→ **208 段流上下文"专家附近"数据**（79+75+54，7-8 min 墙钟）。

训练：425（同条件）+ 109（noisy）+ 208（流上下文）= 742 段，从零 14 epoch（val 0.129）。

| 模型 | 单发 apple | 单发 banana | 连续 3–4 m | 连续 0.6–1.2 m |
| --- | --- | --- | --- | --- |
| `act-noisy`（无流数据） | 8/8 | 7/8 | 1/6 | 1/12 |
| **`act-gnoisy`（+208 段流）** | **8/8** | 6/8 | **16/24 = 66.7%** | **13/28 = 46.4%** |
| `act-wide-4c`（部署） | 8/8 | 8/8 | 9/18 = 50.0% | 7/28 = 25.0% |

**首次在连续作业上超过部署模型**：稀疏喂料 66.7% vs 50.0%，密集喂料 46.4% vs 25.0%
（各 3–4 局汇总；单局 6/14 件，方差较大）。

单发：apple 8/8 持平；banana 6/8（略低于 7/8 门槛，被流数据轻微稀释）。

### 6.26.27 现在能用的方案与下一步

- **可用的连续作业方案**：规则专家 + 本文的目标选择层，0.08 m/s 下 85.7%（3 件/min）、
  超载喂料下 55.6%（10 件/min），已可直接跑（`--policy scripted`）。
- **一个尚未解释的矛盾（下一步必须先查）**：部署模型 `act-wide-4c`（160 段 dwt 示教 +
  DAgger）单发 8/8；而**任何**用本项目新录的 stream/dagger 数据从零训练的模型（ACT 或 flow）
  单发都只有 0–2/4。这不是策略类问题（flow 更差），也不是可学性问题（val 0.044）——
  更像是**录制数据与部署评测之间的某个接口差异**（例如 `build_obs` 的 `held` 标志、
  `instruction` 与 `kinds` 字段、或 off-by-one 对齐）。
  建议用一个 20 行的"数据↔部署一致性测试"先锁死这一点，再谈模型改进。
- **下一步（诊断收敛后的唯一正确做法）**：
  1. **在部署环境里录制**：用 `FruitSort-v1` + 随机 `spawn_spacing`/尺寸（而不是在
     `FruitSortStream-v1` 里录），保证录制状态与部署 runner 的观测构造**完全一致**；
  2. 连续作业的"多件/随机"通过 `spawn_spacing` 和尺寸随机化体现，而不是靠流环境的 slot 机制；
  3. 先过单发 ≥7/8，再看连续 @3–4 m。
- **旧路线（保留备查）**：
  1. 用 `always_stock` 的干净录制把数据补到 ≥100 段（按 7 段/300 s 仿真估，
     需要约 1.2 h 仿真 ≈ 25 min 墙钟，可并行 3 路）；
  2. 从零训练 ACT（`--no-cvae`，30 epoch）→ 先在**单发**上验收 ≥7/8，
     再到连续 @3–4 m（目标 >66.7%）；
  3. 单发不过关就不要看连续指标（本轮多次踩这个坑）。
- **旧顺序（保留）**：
  1. **DAgger 从零训练**（不要微调）：用 6.26.7 的过滤+裁剪标签，**从零**训练而不是 `--init`；
  2. 采集时**只在有效窗口内查询专家**（避免逃逸态标签），并把"从料框上方接管"作为显式分段；
  3. 数据量目标 300–500 段（学习曲线显示 30 段已到 0.20，继续扩的收益要靠 DAgger 打破复合误差）；
- **模型要真正接管连续作业**，六次实验指向三个必要条件（缺一不可）：
  1. **换掉回归式 ACT**：连续流的状态→动作是多峰的（同一画面下"去抓/去放/等待"都合理），
     chunk 回归会学成均值；应改 **Diffusion Policy / Flow Matching**（本项目已在路线图里）；
  2. **数据量与覆盖**：≥500 段，且必须包含"从料框上方接管""目标正在逃逸""多件同框"的状态；
     当前 130 段、且 val 是 train 的 400 倍，属于数据不足而非过拟合；
  3. **标签一致性检查**：先在一小批数据上让模型过拟合到 val≈train（<0.05），再扩规模——
     这是判断"数据可学"的硬门槛，本轮就是被这一步挡住的。
- 生产可用：连续作业用 `--policy scripted`（69–86%），目标选择层已复用。
