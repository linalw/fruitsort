# 为什么"四类混跑"会把每一类都拖垮

> 短答：**主因是一个 bug，不是策略不行。**"这一件已经送达"的判据用的是**夹爪位置**，
> 于是手臂为了**别的类**经过料框时，会把当前目标误判成"已送达"→ 丢弃 → 立刻重选同一件 →
> `runner.reset()` 清空 8 帧历史 → 策略每步都从零开始。
> 单跑时手臂很少无故停在料框上方，混跑时它要为四类各跑一趟框，所以只有混跑被打垮。

## 1. 现象

同一权重（`runs/act-dagger/ckpt.pt`）、同种子、同场景、同一套部署门，只差 `--decline-kinds`：

| 模式 | apple | 其他 | 换目标次数 |
| --- | --- | --- | --- |
| 只做苹果（3 局 × 90 s） | **6/6 = 100%** | 按类让出 | — |
| 四类都接（2 局 × 90 s） | 0/4 | strawberry 3/5、banana 0/3、pear 0/2 | **10 / 90 s** |

苹果从 100% 掉到 0，而"没做"的类并没有变：混跑时每类都要抢同一条手臂。

## 2. 主因（已修）：`at_bin` 判据用错了对象

`StreamController._target_live()` 里有一条"这一件已经结束"的判据：

```python
# 修改前
_tcp = u.agent.tcp_pose.p[0].cpu().numpy()
if hypot(_tcp[0] - bin_x, _tcp[1] - bin_y) < 0.14:
    return False          # 认为"刚把件放进框"
```

**夹爪在料框附近**并不等于"这一件已经在框里"：手臂为了另一件（或刚放下另一件）经过料框时，
当前目标还在带上，却被判成"已送达"。后果是连锁的：

1. 目标被丢弃 → `self.target = None` → `runner.reset()`（清空 `hist=8` 的图像/状态缓冲）；
2. 同一件仍在窗口内 → 下一步立刻被重新选中 → 再丢一次。

实测 trace（`--trace-abandon`）：

```
[abandon] t= 9.3 apple why=at_bin x=-0.39 t_eng=4.77
[abandon] t= 9.3 apple why=at_bin x=-0.39 t_eng=9.30
[abandon] t= 9.4 apple why=at_bin x=-0.39 t_eng=9.33
[abandon] t= 9.4 apple why=at_bin x=-0.39 t_eng=9.37
[abandon] t= 9.4 apple why=at_bin x=-0.38 t_eng=9.40
```

**0.1 s 内连丢 5 次**，`t_engage` 每步被重置，所以连"接管超时"都攒不起来，
整段时间都在"丢弃→重选→清历史"里空转。

### 修复

判据改成"**果实**是否已经在框里"（感知模式下就是跟踪到的位置）：

```python
# 修改后
_ap = self._actor_pos(it["actor"])            # 果实位置，不是 TCP
if hypot(_ap[0] - bin_x, _ap[1] - bin_y) < 0.16:
    return False
```

同条件 90 s 复核：

| | 换目标 | `at_bin` 误弃 |
| --- | --- | --- |
| 修前 | 10 次 | 5 次（全在 0.1 s 内） |
| 修后 | **5 次** | **0** |

### 混跑闭环（3 seeds × 2 局 × 90 s，42 件）

| | apple | strawberry | banana | pear | 掉落 |
| --- | --- | --- | --- | --- | --- |
| 修前（seed 60002，2 局） | 0/4 | 3/5 | 0/1 | 0/1 | 3 |
| **修后（3 seeds，6 局）** | **12/13 = 92%** | 3/11 | 1/11 | 0/7 | **0** |

修后整体送达 16/42 = 38%、吞吐 2.0 件/min，**零掉落**（修前同样时长 3/14 件掉落）。
也就是说：混跑时苹果不是"识别不出来"，而是**每一次都被自身的状态重置打断**。

## 3. 次因（结构性，不能靠改代码解决）：单臂产能

四类同时来料，每类间隔 19–31 s（gap 1.5–2.5 m @ 0.08 m/s）→ **平均 5–8 s 一件**；
而一件的完整循环 ≈ 4.6 s（成功样本实测）+ 1–2 s 行走，已经接近饱和。

后果不是"抓不住"，而是**任何一次重试都会挤掉下一件**：混跑时一次 12 s 的超时，
就足以让同类的下一件直接漏过。这也是为什么单跑 100%、混跑全崩——**排队问题伪装成识别问题**。

缓解手段（部署侧，无需重训）：

- `--decline-kinds`：把做不了的类让给同伴（当前交付口径）；
- `--kind-priority`：高价值/短周期先做；
- 收紧 `--give-up-s`：宁可放弃一件，不要堵住后面三件。

## 4. 第三层：策略的"队列上下文"覆盖不足

模型训练时最多见过 2 类同框，混跑时 4 类同时在窗口 → 队列标志 0.5–0.75，超出分布，
`phase` 会冻结在"接近"。这正是 v1.46 双策略（`--single-ckpt` + `--queue-thr`）想解决的问题：
低队列时用单件模型。我们当前交付命令没有启用它。

## 5. 结论

1. **先修 bug**（已修，见 §2）：混跑掉分的主因是 `at_bin` 误判导致的"每步重置"；
2. **再按产能配类**：单臂同时接 4 类是排队不可行，不是模型不可行——
   要么按类让出（现状），要么多臂；
3. 如果确实要单臂混跑，下一步应做**队列条件化**（用 `--single-ckpt`，或把队列标志纳入训练），
   而不是继续调感知阈值。
