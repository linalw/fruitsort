# 特权信息审计：模型/系统里哪些信号现实中拿不到

> 结论先行：**策略网络本身是"图像 + 状态"的常规结构，但当前喂给它的 57 维状态里
> 有 37 维（65%）来自仿真真值**（水果位置/速度、以及由它们算出的队列标志与抓取几何）；
> 执行层也用了果心位置做残差反馈与安全网。所以现在报告的 **86.7% / 73.9% / 90% 机会内成功率
> 是"oracle 状态"下的结果（≈ 感知完美的上界）**，不是纯视觉可复现的数字。

## 1. 逐项审计（按 57 维状态）

| # | 维度 | 代码位置 | 现实可得性 | 现实替代 |
| --- | --- | --- | --- | --- |
| 7 | TCP 位姿（pos+quat） | `agent.tcp_pose.raw_pose` | ✅ 正运动学 | 关节编码器 + FK |
| 9 | 关节角 qpos | `robot.get_qpos()` | ✅ 编码器 | 同 |
| 1 | 带速 | `u.belt_speed` | ✅（现实中由变频器/编码器给，或直接设定） | 编码器 |
| 32 | **4 类 ×［位置 3、速度 3、active、held］** | `build_obs()` 读 `fruit_actors[k].pose.p / linear_velocity` | ❌ **仿真真值** | 检测+分割+3D 定位+多目标跟踪（速度用差分/卡尔曼） |
| 3 | 相位 one-hot | 策略自己预测回灌 | ✅ 自生成 | 同 |
| 1 | 队列标志（`|x|<0.6` 且在带面的件数 /4） | 由上面的位置算 | ❌ 派生自真值 | 由感知结果算 |
| 4 | 抓取几何 `(TCP − 目标水果) dx,dy,dz,|d|` | 同上 | ❌ 派生自真值（**对精度最敏感，需 ≲1 cm**） | 感知 + 手眼标定 |

图像通道（头顶 + 腕部 RGB，96×96×8 帧）在现实中**可得**（两个相机），但训练用的是
仿真渲染，存在 **sim2real 域差**（光照、纹理、运动模糊、相机噪声）。

## 2. 执行层 / 任务层里的特权信息

| 位置 | 用到的真值 | 现实替代 |
| --- | --- | --- |
| 残差反馈 `target += fb·(fruit − tcp)` | 果心位置 | 跟踪得到的目标位置（或直接用视觉伺服） |
| `z_gate` / 停滞守卫 / 拦截下探 | 果心 z、速度 | 感知 + 滤波 |
| 抓取确认 `|TCP−果心|<4.5 cm`、`fd<0.045` | 果心位置 | 视觉/触觉判据 |
| `is_grasping`（环境/runner） | 手指-物体**成对接触力** | 指端 F/T 或触觉阵列（本项目 v1.17 做过仿真触觉，现实需装传感器） |
| 目标选择（`StreamController`） | 所有在飞件的位置/速度 | 多目标跟踪 |
| 成功/漏检/掉落判定 | 果心位置 | 视觉 + 料框内检测（评测侧，可不进策略） |
| `--scripted-kinds` 专家兜底 | 全部真值 | 仅作上限参照，不能当部署方案 |

## 3. 一个结构性简化（不是"作弊"，但要说清）

观测里**每类只占 1 个槽位**（共 4 个槽），而连续场景里同类可能有 2–3 件在飞。
`StreamController` 在每个时刻把"当前接管的那一件"写进对应槽位，其余件对策略不可见。
现实中可以照搬这个约定（只把目标实例喂给策略），但**多件同类的相互遮挡/排队**必须由
上层调度处理——这也是本项目连续作业评测里 `engaged / declined` 口径存在的原因。

## 4. 这些数字该怎么读

| 数字 | 含义 |
| --- | --- |
| 连续 86.7% / 73.9%、机会内 92% | **oracle（真值）状态**下，策略 + 执行层的上限 |
| 单发 8/8、7/8 | 同上；单发场景里 4 类各 1 件，真值误差更小 |
| 视觉闭环（v0.3，历史） | 苹果+草莓 **0/5**（`docs/perception.md`），当时只有颜色/形状+单应反投影 |

## 5. 要变成"现实可用"，必须补的三件事

1. **感知层替换 `build_obs` 的 32+5 维**：`src/fruitsort/perception/vision.py` 已提供
   `get(kind) -> (pos, vel)` 的同接口实现（颜色族 + 连通域 + 单应反投影 + 匈牙利匹配），
   但历史闭环 0/5；需要升级为「分割（SAM/YOLO）+ 深度/单应 3D + 跟踪」，
   并把**目标件定位误差压到 1 cm 内**（`geom` 的 dz 直接决定何时闭爪）。
2. **域随机化/系统辨识**：相机噪声、光照、运动模糊、控制延迟（已有 `--delay-prob`）、
   质量/摩擦/PD 增益的 sim2real 偏差。
3. **触觉**：至少指端 F/T（用于 `is_grasping` 与滑移检测），否则把相关判据降级为纯视觉。

## 7. 进展：纯感知闭环已经跑起来了（v1.55）

本轮把"感知替换真值"从设想变成可运行：

### 7.1 新东西

| 组件 | 说明 |
| --- | --- |
| `perception/adapter.py::VisionSource` | overhead RGB → `{kind: 替身(pos, vel)}`，与真值同接口；未见类用"刚上料"占位；已夹住时位置跟 TCP |
| `build_obs(..., actors=...)` / `runner.set_actors()` | 策略与执行层不区分真值/感知，**只换物体源** |
| `train_act --view-clip-x -1.10` | 训练时把 x<-1.10 的类也替换成"刚上料"占位，与相机视野一致（否则真机看不到远处水果 → 策略不去拦截） |
| 抓取判定 | 改用**指端接触力**（现实中=F/T/触觉），与物体状态来源解耦 |
| 跟踪修复 | 目标被手臂遮挡 >max_lost 帧后**允许按新位置重新接管**（原来会被旧位置锁死，实测 apple 永远丢） |
| 香蕉/梨消歧 | 从"按进料顺序"改成**按世界长度**（香蕉 ~0.18 m、梨 ~0.09 m），支持随机顺序 |

| --- | --- |
| apple | 0.3 / 0.6 cm |
| strawberry | 0.7 / 1.2 cm |
| banana | 1.5 / 1.7 cm |

### 7.3 纯感知闭环结果（`--perception vision`，act-geom-v）

| 类 | oracle（真值） | **纯视觉** |
| --- | --- | --- |
| apple | 4/4 | **3/4 = 75%** |

- **苹果已经能用"相机 + 单应"闭环抓取并码放**（此前 v0.3 是 0/5）；
- 香蕉/梨仍失败：视觉下策略"先等到拦截点、再下探太晚/太高"，本质还是 6.26.40 记录的抓取几何问题
  （闭爪时 TCP 高于果心 6 cm），叠加 1–2 cm 感知误差后窗口更窄。

### 7.4 距离"真机可用"还差什么

1. **多目标跟踪**：当前每类只跟 1 个 blob，同类多件时靠上层只暴露目标件；需要实例级跟踪（外观/深度特征）。
2. **深度/手眼**：现在用单应 + 已知带面高度；换成 RGB-D 后可去掉"平面假设"。
3. **香蕉/梨的抓取几何**：需要按朝向对准 + 更低的下探（见 6.26.40），否则视觉版也过不了。
4. **sim2real**：光照/纹理/运动模糊/延迟（训练已有 `--delay-prob`）、质量摩擦与 PD 参数辨识。

## 9. 侧视相机补远端（v1.57）

### 9.1 为什么

`overhead` 在带面高度只覆盖 x ≳ −1.1 m，而连续作业上料点在 x≈−1.9…−0.85：
实测 pear @ x=−1.73 投到俯视图像素 (311, **619**) —— **出画**。而 `side` 相机
（1.35, −1.30, 1.15，斜看带面）四类全看得到（同帧 pear → (167, 166)）。

### 9.2 实现

`perception/side.py::SideCamera`：
- **不用单应**（斜视 + 平面假设误差大），而是**深度逐像素反投影**到 3D：
  `p_world = R·(x_cv, −y_cv, −d) + C`，`R,C` 取自 `get_model_matrix()`；
- `depth<=0` 视为无效（真机有空洞，这里同样防御）；
- 分类用 **3D 包围盒对角线**（斜视透视不影响）：实测香蕉 0.107–0.128 m、梨 0.068 m → 阈值 **0.09**；
- 与俯视检测按 8 cm 去重后合并（`RGBDPerception(extra_detectors=[SideCamera])`）。

### 9.3 精度（stream，远端 x∈[−1.85,−1.05]）

| 类 | 检出率 | 3D 误差（均值 / P90） |
| --- | --- | --- |
| banana | 192/310 = 62% | 3.6 / 4.7 cm |
| pear | 188/258 = 73% | 2.7 / 3.1 cm |
| strawberry | 0/77（小、易被挡） | — |

### 9.4 闭环结果（单发，8 局/类）

| 感知 | apple |
| --- | --- |
| oracle（真值） | 8/8 = 100% |
| 俯视单应（v1.55） | 3/4 = 75% |
| 俯视 RGB-D（v1.56） | 2/4 = 50% |
| **俯视 + 侧视 RGB-D（v1.57）** | **7/8 = 87.5%** |

→ **侧视补远端把苹果的纯视觉闭环从 75% 提到 87.5%（真值 100%）**，是目前最好的无真值结果。

### 9.5 还没解决

- **连续作业 + 纯感知**：能端到端跑（无真值），但 120 s 只有 0/6（接管 4 件）。
  目标是"感知 → 目标选择 → 抓取"整链在连续流里稳，目前卡在"感知模式下何时接管/何时下沉"的时序；
- **banana/pear 单发仍 0/4**：抓取几何（下探太晚/太高），与感知无关。


## 10. 感知噪声增强 + 抓取确认自证 bug（v1.58）

### 10.1 噪声增强（`train_act --obj-noise/--vel-noise/--drop-prob`）

按"真机感知有 1–3 cm 误差、偶发丢检"的假设做数据增强并重训 `act-geom-n`：

| 模型 | val | 单发（fused 纯感知）apple | banana | pear |
| --- | --- | --- | --- | --- |
| `act-geom-v`（无噪声增强） | 0.1238 | **7/8 = 87.5%** | 0/8 | 0/8 |
| `act-geom-n`（pos 1.5 cm / vel 0.03 / 丢检 8%） | 0.1279 | 6/8 = 75% | 0/8 | 0/8 |

→ **噪声增强没有收益**（甚至略降）。说明当前瓶颈不是"状态抖动"，而是抓取时序/几何。

### 10.2 发现一个真 bug：抓取确认在感知模式下"自证"

`--grasp-verify` 原本用物体**当前**位姿判断"指面是否到达果身高度"。但感知模式为了在遮挡时
仍能喂给策略，会把**已判定抓住**的物体位置"跟随夹爪"。于是判据变成自证：snap 之后永远满足。

修法：替身同时保留 `raw_p`（未 snap 的估计），抓取确认用 `raw_p`：

| 配置（fused，6 局） | apple |
| --- | --- |
| 无 grasp-verify | 7/8（8 局） |
| grasp-verify（旧：用 snap 后位姿） | 3/6（会把真抓取也否掉） |
| **grasp-verify（新：用 raw_p）** | **5/6 = 83%** |

### 10.3 香蕉/梨在感知模式下的失败循环（trace）

```
t=450  香蕉 x=-0.21  TCP z=0.53  想闭爪（dz=+7cm）
t=480  香蕉 x=-0.15  TCP z=0.49  dz=+2cm → 接触上表面，误判抓住（phase=2）
t=510  香蕉 x=-0.08  TCP z=0.56  verify 发现没抬起 → 回到 phase=0，重新张开
t=540  香蕉 x=-0.03  TCP z=0.53  再下探…
t=570  香蕉 x=+0.03  TCP z=0.47  再次接触上表面 → 又误判
```

→ 平口夹爪从正上方只能压到香蕉**上表面**，反复"碰到→判定→否掉→重试"，水果一路走掉。
**这不是感知问题**，是 6.26.40 记录的抓取几何问题（需要侧向抓取/腕部滚转或在手重定向）。

### 10.4 结论

- 纯感知链路的**近场**已可用（apple 83–88%，真值 100%）；
- **远场**（侧视）可用但被手臂遮挡时丢检；
- **banana/pear 仍是机械/策略层的硬骨头**，与"是否用真值"无关；
- 噪声增强不是当前的有效杠杆（已记录为负结果）。


## 11. 定位修正：香蕉 4.1 cm → 0.5 cm，纯感知香蕉 0/6 → 4/6（v1.59）

### 11.1 根因：像素质心不是物体中心

上一版（8.2）记录 banana 3D 误差 **4.1 cm**，当时归因为"长条质心偏移"，但没量化。
把掩码像素逐个反投影、按轴分解后，误差来源清楚了：

| 误差分量 | banana（改前） |
| --- | --- |
| dx | 1.4 cm |
| **dy** | **3.0 cm（系统性偏 -3.0 cm）** |
| dz | 0.3 cm |

弯曲香蕉的掩码像素质心被"弯月"面积拉向**凹侧**，而训练标签用的是物体的位姿原点（包围盒中心）。
同时 `extent`（用像素 bbox 对角线投到带面）在远端会缩水，把香蕉判成梨：
700 帧里"香蕉"只匹配到 **10** 帧。

另外发现两类**假检测**：料框红边在图像边缘被单应外推成一条 **1.4 m 长的"苹果"**；
这类细长连通域以前也会进跟踪器，是连续作业里"幽灵目标"的来源之一。

### 11.2 改法（`perception/rgbd.py`）

1. 掩码像素**逐个反投影**到带面（向量化单应），先按带面范围筛掉离群像素；
2. **PCA 主轴 → 有向包围盒**：中心取主轴/次轴的 1%–99% 分位中点（不是 min/max，抗离群）；
3. `extent` 改成**主轴长度**（不再用像素 bbox 对角线），分类阈值因此回到物理量纲；
4. 剔除"细线/过大/过稀疏"的连通域（`width<1.2 cm`、`extent>30 cm`、`width>16 cm`、
   `area/(extent·width)` 过小）；
5. 顺带得到**长轴朝向 `yaw`**（mod π，按 2θ 周期平滑），经 `Instance.yaw → _Stub.yaw`
   传给执行层；`yaw_align` 优先用感知朝向（没有才退回真值四元数）。侧视也用 3D 点云主轴给朝向。

> 踩坑：`np.nonzero(m)[::-1]` 是 `(2,N)`，直接 `reshape(-1,2)` 会按 C 序错位（x/y 混行），
> 表现为"所有点都跑到图像外"。`_pixels_to_world` 现在显式转置并断言 (N,2)。

### 11.3 精度（fused，700 帧，每类 2 个 slot）

| 类 | 改前 3D 误差 | **改后** | 匹配帧数（改前 → 改后） |
| --- | --- | --- | --- |
| apple | 0.6 cm | **0.6 cm** | 463 → 463 |
| strawberry | 0.5 cm | **0.5 cm** | 432 → 549 |
| **banana** | **4.1 cm** | **0.5 cm** | **10 → 446** |
| pear | 0.9 cm | **1.0 cm** | 338 → 336 |

- 香蕉的 dy 偏差从 **-3.0 cm → -0.2 cm**，dz 偏差 -0.3 cm；
- 香蕉匹配帧数 ×45：分类不再把远端香蕉当梨。

### 11.4 闭环结果（单发，fused 纯感知，act-geom-v，6 局/类）

| 类 | 改前 | **改后** | 备注 |
| --- | --- | --- | --- |
| apple | 5/6 | 4/6 | 0.6 cm 定位没变，差异在样本噪声内 |
| **banana** | 0/6 | **4/6 = 66.7%** | 定位从 4.1 → 0.5 cm 直接解锁 |
| pear | 0/6 | 0/6 | 但 **4–5/6 能抓起**，问题是搬运中滑脱（`rho` 12–14，摩擦饱和） |

- 香蕉`抓起后掉落 2/6`：说明"抓得到、拿不稳"，下一步是夹持力/抓取点（不是在感知）；

## 12. 腕部相机补"最后 5 cm"：看得见，但精度不够（v1.60，负结果）

### 12.1 动机

11.5 的瓶颈是"单件 12 s（真值 6.5 s）"。trace 显示：手臂伸到目标正上方后**俯视被自己挡住**，

### 12.2 实现

`perception/hand.py::HandCamera`（复用 `side.py` 的深度逐像素反投影 + 颜色/尺寸分类）：

- 每帧重新取 `get_model_matrix()/get_intrinsic_matrix()`（腕部相机会动）；
- 只报**腕部附近**（TCP 水平 35 cm 内）、**带面通道内**（|y|<0.25、x∈[−1.25,0.60]）、
  低高度（z<belt+0.22）的目标 —— 料框在 |y|≥0.28，这条正好把"伸手进框时看到框壁/框里水果"排除；
- 正上方看，中心 z = 顶面 − 半高（`z_center_frac=1.0`，斜视侧相机是 0.4）。

### 12.3 测量（单发 apple，脚本化下探到果心上方 2 cm，65 帧）

### 12.4 闭环：反而更差（负结果）

## 14. "下探塌陷"的真因：遮挡期的超前外推（v1.62）

### 14.1 诊断（逐帧 trace + `ActPureRunner.last_dbg`）

失败局的特征是 `descend≈700 步`、`close=0.62`、全程悬停不闭爪。把"估计 vs 真值"逐帧打出来：

```
t=125 ph=1 grip=-1 tcp=[-0.176,-0.026,0.500] gt=[-0.201,-0.015,0.480] est=[-0.182,-0.028,0.480] |est-gt|=2.4cm dz=+2.0cm
t=150 ph=1 grip=+1 tcp=[-0.106,-0.040,0.497] gt=[-0.142,-0.024,0.481] est=[-0.120,-0.036,0.482] |est-gt|=2.5cm dz=+1.6cm
t=175 ph=1 grip=+1 tcp=[-0.072,-0.052,0.578] gt=[-0.086,-0.038,0.479] est=[-0.070,-0.055,0.479] |est-gt|=2.4cm dz=+9.9cm  ← 又抬起来
```

三点结论：

1. **不是"看不见"**：下探段仍有 ~68% 的帧能看到（俯视）；
2. 看见时 xy 误差 0.2 cm，一旦丢检立刻变成 **超前 2.4–2.5 cm**；
3. 超前量与"带速外推"完全吻合：果实进到两指之间后被**摩擦力拖慢**，不再跟带面同速，
   而感知仍按 `0.08 m/s` 外推 → 每帧多走一点，累计 ~2.5 cm。

策略于是每步都判断"还差 2 cm"，闭爪条件永远差一点；再叠加相位抖动
（grip 在 ±1 来回、dz 从 1.6 cm 弹回 9.9 cm），一次抓取变成 700 步悬停。

### 14.2 两个改法

| 改法 | 位置 | 做法 |
| --- | --- | --- |
| `--close-commit[-map]` | 控制侧 | `phase==1` 且 `-0.5 cm ≤ TCP_z−果心 ≤ 阈值` 且水平 ≤3 cm → **强制闭爪 + 冻结水平目标**，之后 6 mm/步下压到果心 |
| **`--near-hold`（采纳，默认开）** | 感知侧 | 丢检 + 夹爪已压到目标上方（水平 <10 cm）+ 目标是**紧凑水果** → 位置直接取 TCP（不再按带速外推） |

`near_hold` 只对"够大且紧凑"的目标启用（按最近 15 次检测的世界长度**中位数**判）：
苹果 0.065 ✅ / 草莓 0.043 ✗ / 梨 0.09 ✅ / 香蕉 0.17 ✗。原因是：
- 草莓太小：把估计钉在 TCP 上会让策略**提前闭爪**（实测 3/6 → 1/6）；
- 香蕉太长：果心可能离 TCP 好几厘米，吸附会丢掉横向偏移（实测 4/6 → 1/8）。

### 14.3 结果（fused 纯感知，act-geom-v，单发）

| 类 | 基线 | close-commit | **near-hold** |
| --- | --- | --- | --- |
| apple | 4/6 | 5/6（10 局 9/10） | **8/8 + 6/6 = 14/14 = 100%，0 掉落** |
| strawberry | 3/6 | 1/6 | 3/6（被尺寸闸排除，行为不变） |
| banana | 4/6 | 0/6 | **5/8（前 6 局逐帧与基线完全一致：4/6）** |
| pear | 0/6 | 0/6 | 0/6（抓得起 4–5/6、搬运滑脱） |

**apple 单件处理时间 20.4 s → 8.5 s**（真值 6.5 s），成功率 100%（真值 100%）——
这是"纯感知可用"的第一个闭环证据。

### 14.4 连续作业（稀疏 3–4 m，3 局 × 60 s，seed 60001）

| 指标 | v1.61（无 near-hold） | **v1.62（near-hold）** |
| --- | --- | --- |
| 送达 / 上料 | 4 / 15 | **7 / 15** |
| 机会内成功率 | 4/11 = 36.4% | **7/13 = 53.8%** |
| 让给同伴 | 4 | 2 |
| 吞吐 | 1.33 件/min | **2.33 件/min** |
| 每类 | apple 2/4、straw 1/3、banana 0/4、pear 1/4 | **apple 3/4、straw 3/3**、banana 0/4、pear 1/4 |

### 14.5 结论

- "下探塌陷"的根因在**感知的遮挡外推**，不在策略；修在感知端之后不再需要按类调控制参数；
- 吸附规则必须**按目标尺寸设闸** —— 这也解释了为什么之前所有"按类调参"只能在一两类上奏效；
- 剩余短板：pear（摩擦/形状，抓得起 4–5/6 但夹不住）、banana 在连续流里 0/4（单发 5/8 →
  流里的移动+队列切换把它打没了，下一个要查的就是这里）。


## 15. 连续流里 banana 0/4：定位、四条被否的规则、以及"按朝向让件"（v1.63）

### 15.1 逐帧复现（同种子 60001–60003，fused + near-hold + `last_dbg`）

3 局共 4 个 banana 目标，全部"伸得到、抓不住"：

| 目标 | 结果 | 最近 xy 距离 | 该刻 dz | 相位1 时估计误差（中位） |
| --- | --- | --- | --- | --- |
| ep0 id3 | missed | 0.1 cm | +4.5 cm | 3.0 cm |
| ep1 id3 | dropped | 0.5 cm | +10.4 cm | 6.0 cm |
| ep1 id5 | （未结束） | 0.2 cm | +7.4 cm | 3.9 cm |
| ep2 id3 | dropped | 0.4 cm | +10.2 cm | 4.7 cm |

三条事实：

1. **不是"够不到 / 拦截太晚"**：四次都把手伸到了果心正上方（xy 0.1–0.5 cm）；
2. 相位 1（dz<4 cm）时估计误差 **3–6 cm，y 偏 −1.4…−1.8 cm**：长条目标被尺寸闸排除在
   near-hold 之外，遮挡期只剩"带速沿 x 外推"，**横向/沿轴的偏移没人补**（部分可见的
   香蕉掩码中心会沿长轴滑，长轴本身带 y 分量）；
3. 12–23 步"抓住"发生在 **dz=+10 cm**：近似判据（离得近+闭爪）被 3–6 cm 的估计误差骗了
   → 搬运空气、果实从指间滑走（dropped / missed）。

### 15.2 四条规则的效果（同种子复核；单发 banana 基线 4/6=5/8）

| 规则 | 单发 banana(6) | 流内 banana | 判定 |
| --- | --- | --- | --- |
| 长条拦截点**恒定**前移 0.25 s | **0/6**（掉 6） | — | ❌ 把瞄准点推到长条一端 |
| 前移 + 距离**衰减**（0.15 m 内归零） | 2/6 | 0/1 | ❌ 仍回退 |
| 抓取判据只认**真实接触**（`--grasp-proxy auto`） | 3/6 | 0/4（整局 6/15） | ≈中性，不解决 |
| 按类抓取高度 `--z-bias -0.01 / -0.02` | 0/6 / 0/6（各掉 4） | — | ❌ 更低反而更差 |

→ **"长条目标拦截点按带速前移"在本配置下是负结果**：`fb=0.7` 已经把反馈滞后补掉，
再前移只会让瞄准点落在长条的一端（抓尖端必掉）。

### 15.3 可行的一条：按**长轴朝向**决定要不要接这件（`--decline-yaw`）

感知现在给得出长轴 `yaw`，且**香蕉的 yaw 极准**（420 帧实测：中位误差 **0.3°**、P90 0.5°；
苹果 28°/草莓 24°，因为接近圆形、主轴本来就没定义）。

平口夹爪沿世界 y 闭合，若香蕉长轴也接近 y（`|sin yaw|` 大），只能夹住两端 → 必失败。
现场语义：**不接这种件，让给旁边朝向更合适的臂**（记账里算 declined）。

| 配置（3 局 × 60 s，seed 60001） | 送达 | 机会内 | 让给同伴 | 每类 |
| --- | --- | --- | --- | --- |
| v1.62（无朝向闸） | 7/15 | 7/13 = 53.8% | 2 | apple 3/4、straw 3/3、banana 0/4、pear 1/4 |
| **`--decline-yaw 0.64`（采纳）** | **9/15** | **9/11 = 81.8%** | 3 | **apple 4/4、strawberry 3/3**、banana 0/4（全部让出）、pear 2/4 |
| `--decline-yaw 0.80`（放宽） | 5/15 | 5/10 = 50% | 4 | apple 3/4、straw 1/3、banana 0/4（接管 3 件全失败，1 掉落）、pear 1/4 |

- 用**默认配置复跑**（不加任何 flag）逐字复现：送达 9/15、机会内 9/11 = 81.8%、让出 3；
  逐局"机会内每类"：ep0 `banana 0/0`（全部让出）→ ep1 `0/0` → ep2 **`0/1`（接管了 1 件仍失败）**；
- 严格闸（0.64）把 **4 件香蕉中的 3 件判为"不该接"**（这批随机 yaw 的 `|sin|` 中位 0.72，
  均匀随机的期望值本身就是 0.707）→ 交付 0，但**机会内成功率从 53.8% 提到 81.8%**；
- 放宽到 0.80 时接管了 3 件，**仍然 0 成功（1 件掉落）** → 说明剩下的失败不是朝向，
  而是 15.1 的"遮挡期估计 3–6 cm + 平口夹爪夹长条顶端"。

### 15.4 结论（诚实版）

- 连续流 banana **仍未做到 ≥2/4**：条件允许时（朝向可接）接管 3 件、0 成功；
- 但这一轮拿到了**可用的现场规则**：按长轴朝向**让件**，机会内 53.8% → **81.8%**，
  送达 7/15 → **9/15**，且不牺牲苹果/草莓（4/4、3/3）；
- banana 的剩余瓶颈是**机械 + 深度**：需要（a）能绕长轴旋转的夹爪/吸盘，或
  （b）训练期腕部偏航增强（`yw-*` 那批数据，见 6.26.44）后执行期对准 —— 二者都超出
  "感知层"能单独解决的范围。

## 17. 腕部对准改成闭环（v1.65）：残差 <5°，但**腕部响应太慢**（负结果）

- phase 0/1 期间每 10 步重算一次 **mod π** 的指面轴误差（v1.64 已修的 wrap 保留），

- 对准的**计算**已经不是问题（残差 1.3–5°，<10° 达成）；
- 真正的墙是**执行器时序**：`pd_ee_pose` 在平移阶段几乎不执行姿态指令（实测 170 步不动），

## 18. 两段式控制：先原地对准再进场（v1.66）—— 对准成了，目标仍差一步

2. **换末端**：吸盘/软指对弯香蕉远比平口夹爪稳（`rho` 40 说明摩擦已饱和）；
3. 或双臂并行（香蕉交给第二只臂），这正是 v1.54 引入"机会内/让给同伴"口径的前提。


## 20. 把预转挪到空档期（v1.68）：机制成立，但被"其它类接管时腕部回正"抵消

### 20.1 实现

- `StreamController._idle_align_yaw()`：**没有可接的件时**（`target is None`），用
  "下一件香蕉"的感知长轴算目标姿态，闭环（gain 0.9、死区 5°）把腕部转过去；
  待命动作下发 `HOME_EULER[2] + idle_yaw`；
- `_yaw_cache[item_id] = idle_yaw`：接管该件时把它当作 `_yaw_target` 初值
  → 窗口内**第一步就是满指令**（不用再爬坡）；香蕉的接受范围放宽到 x∈(−1.15,−0.30)。

所以一旦下一个接的是苹果/草莓，执行层立刻把腕部命令回 HOME —— 空档期攒下的预转被清零；
而按 `--kind-priority`，香蕉总是排最后。

### 20.4 结论：验收仍未达成；瓶颈已经从"对准"彻底转到**末端执行器**

- 流内 banana 最好 **1/4**（v1.66）、多数 **0/4**；apple 3/4（要求 4/4）；
- 三条量化事实说明问题不在感知/对准：
  1. 对准残差已 **0.1–2°**（进场前），抓取瞬间 2–6°；
  2. 单发香蕉仍只有 **2/6**，其中 **3/6 是"抓起后掉"**（`rho` 14，`slip` 33 cm）——
     平口夹爪夹弯香蕉，摩擦已饱和；
  3. 接香蕉会挤掉苹果/草莓（apple 从 4/4 → 3/4；`strawberry 0/0` 出现过）——

## 21. 让预转"活过"非香蕉件（v1.69）：机制成立，但苹果/草莓付代价

### 21.1 实现

- `yaw_align_hold=True`：当目标**不在**对准范围（苹果 0.065/草莓 0.043 < 0.12）时，
  不再把腕部命令回 HOME，而是**保持** `_yaw_cmd`（含搬运段）；
- `yaw_hold_fade=0.12`：可选，距果心 12 cm 内把保持量线性淡出到 HOME，

- 控制器在接管任何件时把 `_yaw_cmd/_yaw_target` 播种成 `_idle_yaw`（缓存空档期的朝向）；
- 顺带修掉一个崩溃：切换目标后的第一步若在搬运/下探中，`_yaw_target` 还是 None →
  `_yaw_cmd` 变成 None（`yaw += None`）→ 已加 None 保护。

   需要新 robot uid、吸附/释放动作空间、重录 40–60 段 + 重训 ~40 min；
2. **双臂并行**：香蕉交第二只臂（v1.54 的"机会内/让给同伴"口径本来就是为多臂设计的）。

两条都超出"纯感知层"能单独解决的范围，需要确认投入哪条。


## 22. 非长条目标的"保持量"扫描（v1.70）：cap 0.3 最好，但仍差一步

### 22.1 实现

`--yaw-hold-frac`（比例）与 `--yaw-hold-cap`（上限，rad）：非长条目标上保持的偏航
`hold = clip(_yaw_cmd * frac, ±cap)`，再按 `yaw_hold_fade` 淡出；默认 frac=1、cap=0（=v1.69 全保持）。

### 22.2 扫描结果（同种子 3×60 s，`--decline-yaw 0 --yaw-align --yaw-align-extent 0.12`，逐类机会内）

| 保持量 | 送达 | 机会内 | apple | strawberry | **banana** |
| --- | --- | --- | --- | --- | --- |
| 全保持（≈0.95 rad，v1.69） | 4/15 | 30.8% | 2/4 | 1/3 | **1/4** |
| **cap 0.5 rad** | 5/15 | 41.7% | 3/4 | 2/3 | 0/4 |
| **cap 0.3 rad** | **6/15** | **46.2%** | 3/4 | 2/3 | **1/4** |
| 不保持（回 HOME，v1.68） | 6/15 | 50.0% | 3/4 | 3/3 | 0/4 |

- cap 0.3 是扫描里最好的（送达、机会内、banana 都是非零的最高档），但它与"apple 4/4 + strawberry 3/3"
  仍然互斥：不接香蕉时（v1.63）apple 4/4、straw 3/3、9/15，一旦把香蕉纳入就掉到 3/4、2/3；

  （7.0 s、`rho` 14.1、掉 3/6），v1.69 全保持下另一轮为 4/6 → 33–67% 波动。

### 22.3 结论：验收仍未达成；三条硬事实

1. **感知/对准已到顶**：定位 0.5 cm、香蕉 yaw 0.3°、进场前残差 0.1–2°；
2. **苹果 4/4 与"接香蕉"互斥**：60 s×3 = 15 件，香蕉每件 6–11 s，接 4 根就吃掉 30–45 s；
   任何 yaw 策略都无法同时满足"香蕉≥2/4 + apple 4/4 + straw 3/3"（数据显示二者此消彼长）；
3. **香蕉抓取稳定性**是最后一环：单发上限 4/6、抓起后掉 1–3/6、`rho` 14–40（平口夹爪 + 弯果身）。

### 22.4 需要决策

满足全部验收的唯一路径是**换末端（吸盘/软指）或双臂**，两者都需要新 robot/动作空间 + 重训：
- 吸盘：`eval_act_suction.py`、`dexterous_sort*` 有现成基线，估 40–60 段录制 + 40 min 训练；
- 双臂：v1.54 的"机会内/让给同伴"口径本就是多臂设计，可直接把香蕉派给第二臂。
在此之前部署仍取 **v1.63**（9/15、机会内 81.8%）。


## 23. 吸盘/软末端通路（v1.71）：单发香蕉 4/4=100%（4.6 s），但流内搬运还不成立

### 23.1 实现（复用本仓库已验证的吸盘语义）

- `ActPureRunner(suction=True)`：**接触即吸**（TCP 距果心 <5 cm 直接附着，不再依赖模型闭爪时机——
  那正是平口夹爪失败的地方）；附着后水果跟 TCP（`offset` 保持）；到目标框上方（±7 cm、z<0.62）
  **自动吹气释放**落到框底（env 判 `in_bin` → delivered）；
- `--suction / --suction-radius`（`stream_eval` / `eval_act_pure`）；
- `FruitSortStream-v1` 新增 `item["held"]` 语义：被吸住的件**停带**（否则带面驱动每步
  `set_pose` 覆盖附着，等于没吸上）。

### 23.2 路上修掉两个真 bug（都有 trace）

| bug | 现象 | 修法 |
| --- | --- | --- |
| 吸盘状态被接触判据覆盖 | `att=True` 但 `phase` 一直是 1/0，永不走搬运 | 在 contact/proxy 赋值后**重新断言** `grasping = attached` |
| 流场景带面驱动覆盖 `set_pose` | 附着后水果位置不跟 TCP（`gt≠tcp`） | 控制器把 `attached` 同步成 `item["held"]`，env 停带 |

### 23.3 结果

| 场景 | 平口夹爪（对照） | **吸盘** |
| --- | --- | --- |
| 单发 banana（4 局） | 2/6（掉 3–4） | **4/4 = 100%，0 掉落** |
| 单件处理时间 | 7.0–8.0 s | **4.62 s**（P90 4.87 s） |
| 法向力/摩擦利用 | rho 14–40 | **rho ≈ 0**（无挤压） |
| 连续流 3×60 s（同种子，decline-yaw 0） | banana 0–1/4、9/15 | **0/15（附着了但没送到）** |

trace（流内，ep0）：`t=180 att=True held=True ph=2`，水果已跟着 TCP；
但之后手臂一直在 `x≈−0.15, y≈−0.25` 附近**来回**，而苹果框在 `x=−0.46` → 永远进不了
"框上方 ±7 cm"，`suction_off=0`，一件都没送达。

### 23.4 结论与下一步（需要决策）

- **吸盘把"抓不住"彻底解决了**（单发 4/4、0 掉落、4.6 s、无挤压），这正是前 8 轮里
  香蕉失败的主因；
- 但**流内搬运**用的是"为平口夹爪训练"的策略：在流上下文里它的搬运段不往框里走
  （`x` 差 30 cm 且来回），所以流内 0/15；

  → **56 点标定，重投影 mean 0.72 px / max 2.72 px**，存 `assets/calib/overhead_homography_gemini.npy`。

### 28.2 远端（x<−1.0）验证

| 头部相机 | strawberry | banana | pear |
| --- | --- | --- | --- |
| 旧 fov1.02 / 640 | 53%（0.1 cm） | 15%（0.7 cm） | 15%（0.6 cm） |

### 28.3 重录 + 重训（完成，但数据量不够）

- 用新相机重录 **43 段**夹爪示教（apple 12 / strawberry 12 / banana 10 / pear 9，
  `record_demos.py --images --instruction <k>`）；
- 从零训（`runs/act-gemini`，12,430 窗口，20 epoch）：best val **0.3065**（旧模型 0.1238）；
- **从 act-geom-v 微调**（`--init --reuse-norm`，lr 1e-4，12 epoch）：best val **0.1551**。

### 28.4 评测（新相机 + 微调权重）

| 配置 | 单发 banana | 同种子 3×60 s 流 |
| --- | --- | --- |
| `act-gemini-ft` + 新相机 + 头部 RGB-D | 0/6 | 0/15（apple 0/4、banana 0/4…） |
| 对照：`act-geom-v` + 旧相机 + 头部 RGB-D | 0/4 | 4/15（apple 4/4） |
| 对照：`act-geom-v` + 旧相机 + **fused** | 1/4 | 9/15（v1.63） |

### 28.5 结论（如实）

1. **"头部 = Gemini 335"这一条真正落地了**：相机参数可切（`FRUITSORT_HEAD_FOV/Z/RES`）、
   标定流程支持新相机、草莓远端命中 53%→**85%**、误差 0.1 cm；
2. **夹爪策略在新相机上不可用**：43 段（12.4k 窗口）远少于可用模型所需的量级
   （v1.63 用 745 段 / 19 万窗口），从零训 val 0.31、微调 0.155；单发与流内都是 0；
3. **按类闭爪高度门**（`--close-z-gate-map`）已实现，但实测它会**阻止闭爪**
   （`抓取过 0~1`）——语义是"不到高度就强制下探"，需要和模型一起重训才有效，暂默认关闭；
4. 目前**约束内最好成绩仍是 4/15（apple 4/4）**（旧相机 + act-geom-v + 纯感知选目标）。

### 28.6 下一步（明确的量级）

- 用新相机录 **300–500 段**（4 类 × 75–125，含随机带速/尺寸/朝向），按 v1.63 配方从零训
  （约 1.5–2.5 h 录制 + 40 min 训练），再做"闭爪高度"的按类 CT（`close_z = 果心 − 0.3×半高`）
  ——当前 43 段只能验证"流程通了"，不能验证"能用"。


## 29. 300+ 段重录 + ROI 裁剪（v1.77）：找对了病灶（视觉输入是瞎的），但策略仍未跑起来

### 29.1 做了什么

| 步骤 | 结果 |
| --- | --- |
| **284 段**（gem2-*，Gemini 相机 1.62/1280×960 + 新标定，4 类 80/80/66/58） | 从零训 `runs/act-gem2`：71,890 窗口，best val **0.1253** |
| 评测 | 单发 banana 0/6；同种子流 **2/15**（apple 2/4，其余 0）——**非苹果仍全 0** |

诊断：把"头部整幅压到 96×96"的像素量算了一遍 —— 宽视场下**高饱和（果实）像素占比 0.0%**
（苹果只剩 ~1 px），CNN 分支等于瞎的；这不是训练量的问题。

### 29.2 ROI 裁剪（以目标为中心 0.5 m 窗口）

- 新增 `src/fruitsort/perception/roi.py::RoiCrop`（world→pixel 用带面单应，replicate 边界）；
- **录制端**（`record_demos.py --roi-m 0.5`）与**部署端**（`ActPureRunner` 里同一变换）一致；
- 效果（同一帧）：`gem2-apple` 高饱和像素 **0.0%** → `roi-apple` **3.7%**（果实 ~25×25 px@128，≈19 px@96）。

### 29.3 重录 + 重训（204 段 roi-*：60/60/47/37）

`runs/act-roi`：48,794 窗口，14 epoch，**best val 0.0986**（历史最好，优于 act-geom-v 0.1238）。

### 29.4 但部署仍崩（负结果，已用 trace 定位）

| 配置 | 单发 banana | 流 |
| --- | --- | --- |
| act-roi + 新相机 | 0/6（`Fn≈0`） | 0/15 |
| act-roi + **旧相机**（ROI 下两相机图像几乎等价） | 0/4（`Fn 0.2N`） | — |

trace：手臂在**离果子 5–7 cm 处悬停**，相位 0/1 抖动、夹爪开合抖动 —— 典型的"下探塌陷"，
**不是**感知（`near_hold` 已把 xy 贴到 TCP，dz 仍有 5–13 cm 却不下降）。

推断：ROI 把**全局上下文**裁掉了（带面走向/其它果/框的位置），而相位头正是靠这些学"何时下探"；
另外录制/部署两端的 ROI 中心依赖标定文件（`FRUITSORT_CALIB`），一旦不一致，裁剪窗会偏。

### 29.5 按类闭爪高度：已进训练（`--close-z-loss 0.5 --close-z-frac 0.3`）

闭爪步的目标 z 用 hinge 压到"果心 − 0.3×半高"以下。实测该损失全程 **0.0000**（约束已由示教满足），
说明"闭爪偏高"不是示教数据的属性，而是**部署时策略没走到位**（见 29.4 的悬停）。

### 29.6 结论与下一步

- 约束内目前最好仍是 **4/15（apple 4/4）**（旧相机 + act-geom-v + 纯感知选目标）；
- 本轮**确认了真正的病灶**：宽视场把果实压成 1–2 px → 视觉分支失效；ROI 是对的方向
  （像素 0.0%→3.7%、val 0.0986 最好），但**只给 ROI 会丢掉相位所需的全局上下文**；
- 下一步（明确）：**双路图像** —— 全局（整幅 96×96，给相位/上下文）+ ROI（目标局部，给细定位），
  两路分别过 CNN 再拼 token；同时把 ROI 的标定文件写死进 ckpt，避免录制/部署不一致。


## 30. 双路图像（全局 + ROI）落地（v1.78）：val 0.036 最好，闭环仍 0

### 30.1 实现（模型/数据/部署三处一致）

| 位置 | 改动 |
| --- | --- |
| `ActConfig.use_roi` | 第三路图像 token（全局 + 腕部 + ROI 三路**共享同一个 CNN**，各自有 `view_type` 嵌入） |
| `ActPolicy.encode/forward(..., imgs_roi=)` | 因果 mask 里按 `n_per_t` 排列，token 数随路数自适应 |
| `image_dataset` | 读 `roi_jpg`（流录制缺帧会自动对齐长度） |
| `record_demos` | 同时存 `overhead_jpg`（全局 128）+ `roi_jpg`（0.5 m ROI 128） |
| `stream_eval --record --roi-m` | 连续流录制也存 ROI（脚本专家） |
| `ActPureRunner` | `self.roi_buf` 历史 + 传 `imgs_roi`；**与录制端同一 ROI 变换** |

### 30.2 数据与训练

- **163 段**双路单发示教（45/45/38/35，Gemini 相机 + 新标定）；
- **60 段**连续流脚本专家片段（`stream_eval --record --roi-m 0.5`）；
- `runs/act-dual`（仅单发数据）：40,782 窗口，best val 0.1552；
- **`runs/act-dual2`（单发 + 流片段）**：84,903 窗口，**best val 0.0360**（历史最低）。

### 30.3 评测（新相机 + 头部 RGB-D + 纯感知选目标）

| 配置 | 单发 banana | 同种子 3×60 s 流 |
| --- | --- | --- |
| act-dual（无流数据） | 0/6 | 1/15（apple 1/4） |
| **act-dual2（含流数据）** | 0/6 | 0/15（4 掉落） |
| act-dual2 + `--close-commit-map`（几何闭爪） | — | 0/15（`抓取过` 2–4） |

### 30.4 结论（如实）

- **双路图像这条路本身工作正常**（val 0.036 说明拟合很好、ROI 让"果实像素 0.0%→3.3%"）；
- 但**闭环仍然 0**：val 与闭环脱节 —— val 里含与评测同分布的流片段，指标被抬高；
  实际闭环里模型自身误差累积后不再"下探/闭爪"，runner 的 `close-commit` 也救不回来；
- **约束内最好成绩依旧是 4/15（apple 4/4）**：旧相机 + `act-geom-v` + `--perception-targets`
  + `--decline-yaw 0.64`。

### 30.5 建议（需要换思路，不是继续加数据）

1. **DAgger 式纠偏**：用当前策略跑流、专家在"该下探/该闭爪"处接管，把纠正帧加入训练
   （仓库已有 `dagger_act.py`/`collect_self_distill.py` 可复用）——这是修复"val 好但闭环 0"的标准手段；
2. 或把"何时下探/闭爪"从回归头里拆出来做**分类器**（用 `descend_boost` 的相位标签），
   推理时以相位头为主导（runner 现有关闭相位反馈的开关也在）；
3. 末端/机械不变（夹爪），香蕉允许低。


## 31. DAgger 纠偏（v1.79）：苹果 3/4=75%（✅），草莓/香蕉仍 0

### 31.1 新增 `scripts/dagger_stream.py`

- **学生跑闭环**（当前 ckpt + 头部 RGB-D 感知 + `--perception-targets`），
  专家（马尔可夫几何规则，同 `dagger_act.py`）在**学生访问到的状态**上打标：
  追拦截点 → x/y 对齐且进抓取区就"下探到果心 + 闭爪"；已抓住就"搬框 → 下放 → 开爪"；
- 保存的是**感知状态** `build_obs(u, kind, actors=objs)`（与部署同源）+ 三路图
  （全局 128 / ROI 0.5m / 腕部），`instruction` 固定为 `--kind`；
- 一局只追一类（其余三类照常在场当上下文），每局 55 s。

### 31.2 采集结果（学生全失败 —— 正是需要的失败状态）

| --- | --- | --- | --- |

### 31.3 训练（DAgger 数据并入 + 微调）

`dual-*(163) + dual-stream-sel(59) + dagger2-*(8)` = 109,473 窗口，

## 32. DAgger 第 2 轮（v1.80）：**回退**（apple 3/4 → 0/4），暴露 DAgger 循环不稳定

### 32.1 本轮做的

- 草莓专家规则改成"**果心 − 半高 + 0.5 cm** 闭爪"（与训练侧 `--close-z-loss` 同向）；
- 用 act-dagger 再采 3 类 × 3 局（strawberry 1334 帧 / banana 1108 / pear 945，学生仍全部失败）；
- 累积数据（dual 163 + stream 59 + dagger2 8 + dagger3 9 局）微调：
  `--init runs/act-dagger/ckpt.pt --reuse-norm`，lr 1e-4，6 epoch，`--descend-boost 5`，
  best val **0.1392**（第 1 轮 0.1406，基本持平）。

### 32.2 评测（同种子 3×60 s，`--decline-yaw 0.80` 以便多接香蕉）

| 轮次 | apple | strawberry | banana | pear | 总送达 |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮 act-dagger | **3/4 = 75%** | 0/3 | 0/4 | 0/4 | **3/15** |
| **第 2 轮 act-dagger2** | **0/4** | 0/3 | 0/4 | 0/4 | **0/15** |

### 32.3 结论：DAgger 循环当前**不稳定**（不是"再加一轮就好"）

- val 几乎没变（0.1392 vs 0.1406），但闭环从 3/15 掉到 0/15 —— 说明单看 val 无法判断；
- 可能原因：① 每轮数据分布随学生策略漂移，微调把它推向新分布而丢掉旧能力（灾难性遗忘）；
  ② 草莓规则改低后，其余类在 `descend_boost 5` 下被相对稀释；
  ③ `--decline-yaw` 从 0.64 改成 0.80 让香蕉更多进入（占用了抓取窗口）。

### 32.4 下一步（改进 DAgger 循环本身，已明确）

1. **每轮都从同一个"学生基线"重训**（不做连续微调），数据集只增不减，lr 回到 3e-4；
2. 或**按类路由**（apple/strawberry 用一个模型、banana/pear 用另一个），避免互相稀释；
3. 评测固定 `--decline-yaw`，不随轮次变，保证可比；
4. 每轮记录"新增帧数 / 闭环各类送达"，val 只作参考。
